## 发现清单

### H1（bug）watchdog：respawn 失败一次后实例永久失去看护，与「无限重试」使命冲突

`src/watchdog.rs` `handle_death`（watchdog.rs:325-391）：

1. 函数开头 `imp::close_handle(w.handle)`（:330）后，respawn 失败分支把 `w` 原样
   push 回 `watched`（:386）——句柄是**已关闭的悬空值**，未置 0。
2. 此后该实例的死亡 watcher 已消费（死亡事件只发一次），`adopt_scan` 因
   `self.watched.iter().any(|w| w.port == entry.port)` 去重（:259）**永远跳过**它，
   注释声称的「下轮 adopt_scan 视注册表情况重试」（:383）不会发生；
   `health_scan` 对僵尸条目也走不到任何出口（心跳节随进程死亡消失 → None →
   continue，watchdog.rs:306）。
3. 后果链：一次 respawn 失败（端口被占、配置文件被删等）→ 该实例崩溃后无人重拉、
   `consecutive_failures` 不再累计、crashloop 上限逻辑永不生效——看门狗对它失效，
   只剩人工 `aproxy restore`。
4. 同根问题：respawn 成功但 `open_sync_handle` 失败分支 `w.handle = 0` 且不挂
   death watcher（:369-375），注释称「adopt_scan 下轮会补挂正确句柄」——同样被
   去重挡死，此后该实例死亡无感知、永不重拉。
5. 附带：respawn 失败分支还会令 `maybe_idle_exit` 的 watched 非空 → 看护者
   永不自灭。

修复方向：respawn 失败时不 push 回 `watched`；`consecutive_failures` 迁移到以
port 为键的独立 map（跨收养周期保留计数）；`adopt_scan` 去重只认「handle 有效」
的条目。同时 `close_handle` 后立即将 `w.handle` 置 0（避免悬空句柄值被后续
`terminate_handle` 复用误杀的理论风险）。

### H2（回归）unix cfg 编译错误：HeartbeatWriter 引用已删除的 `port` 字段

- unix 版 `HeartbeatWriter` 定义只有 `_shm_fd` 字段（watchdog.rs:612-613）。
- 但 unix `imp_heart::create_heartbeat` 构造 `HeartbeatWriter { port: ..., _shm_fd }`
  （:824），`heartbeat_store` 读 `writer.port`（:830）→ E0560/E0609，
  **unix 目标无法编译**。
- 根因：W4 提交 773996e「HeartbeatWriter 删未读 port 字段」在 Windows clippy
  零警告清理时删除了字段，漏改 unix 分支（Windows CI 不编译 `#[cfg(unix)]`）。
- 加重因素：`.github/workflows/` 配置了 ubuntu/macos `cargo check --all-targets`，
  但**本仓库没有 git remote，CI 从未运行**——防线形同虚设。TODO「unix 分支实测」
  应升级为「先让 unix check 真正跑起来」。

修复方向：unix 结构体加回 `port: String` 字段（或改用 `/dev/shm` 路径推导）；
推动仓库挂 remote 让 CI 实际运行。

### H3（skill 误导）behaviors.md「4xx 不重试」与代码/测试三方矛盾

- `references/latest/behaviors.md` 不重试清单第 1 条：「4xx（除特定误配置场景……）」。
- 代码事实：`retry::is_retryable_status` = `(400..=599).contains`（retry.rs:39-41），
  `proxy.rs` 模块注释「4xx 同样视为易发瞬时错误」（proxy.rs:6）、
  `should_retry_response` 第一步即状态码判定（proxy.rs:956），测试
  `retryable_status` 断言 400/401/403/404/429 **全部重试**。
- 影响：skill 读者（agent）会误判 4xx 行为——实际 4xx 会无限重试，而非透传。
- 附带：SKILL.md 心智模型与 README 特性列表的触发条件「网络错误、5xx、错误 JSON」
  均漏 4xx（不完整而非矛盾）。

修复方向：behaviors.md 该条改为「4xx 会重试（原型决策：限流/临时鉴权波动等
瞬时错误常见；确定性的 4xx 也重试是已接受的代价）」，并同步 SKILL.md/README。

### M1（语义盲区）无限重试中的实例会被 `stop idle` / `status --idle` 误判为闲置

- `last_activity_secs` 只在收到请求时 store（proxy.rs:753-759）；重试循环持续
  数小时期间不更新。`stop idle` 按 `now - last_activity >= idle_timeout_secs`
  筛选（commands/stop.rs:40-42）→ 请求 30 分钟前到达、至今仍在无限重试的实例
  会被判闲置并停止（10s 宽限强退中断在途重试）。
- 与项目使命「无限重试、不中断」直接冲突：正是最需要保障的实例反而最先被杀。
- 修复方向：重试通道每轮 attempt / 退避 sleep 时也更新 `last_activity_secs`
  （一条 Relaxed store，零热路径成本），语义变为「最近一次收到请求或仍在处理」。

### M2（稳健性）看护者主循环串行阻塞 → claim 过期 → 被竞争者误杀 → respawn 丢失

- `tick()` 串行 await：`handle_death` 内退避 `sleep`（第 8 次失败起 ≥128s，
  watchdog.rs:359）+ `respawn_instance` 最长 8s（:514）+ `health_scan` 的
  `ipc_ping` 最坏 ~9.6s（3 次 × 3s 超时，daemon.rs:169-184）全部阻塞主循环；
  期间 `refresh_claim` 停摆。
- claim 新鲜阈值 = 3×周期 = 90s。多实例场景下：一个实例 crashloop 退避 sleep
  >90s → claim 过期 → 其他守护的自检（server.rs:116-146，每 5 分钟）按选举规范
  补种新看护者 → 新看护者经 `serve()` 的「假死前任」路径
  `terminate_verified` **杀掉卡在 sleep 的现任**（watchdog.rs:545-556）→
  其 pending 的 respawn 永久丢失；新看护者 `adopt_scan` 只收养**活进程**
  （is_aproxy_process 拒绝死实例，:268）→ 该崩溃实例无人拉起。
- 单实例场景无竞争者，sleep 完成后正常 respawn——此风险需要 ≥2 实例 + 其一
  连续失败 8 次以上才触发，概率低但后果是看护失效。
- 修复方向：退避 sleep 与 respawn 移出主循环（每实例独立任务）或 sleep 期间
  并发续写 claim（select 竞速）。

### L1（措辞偏差）watchdog_stale_after_cycles 文档语义与实现不完全一致

- settings.rs:65-66 与 settings-json.md： 「连续 N 轮心跳扫描都没更新**且 IPC
  ping 也失败**，才判定挂死」——读作「连续 N 轮 ping 失败」。
- 实现：单轮扫描内 stale 阈值 `(N+1)×scan` 吸收了容忍，ping 只打一轮
  （内含 3 次 IPC 探测），watchdog.rs:311 注释自认「×1」。实际效果近似
  （stale 窗口已含 N 倍容忍）但措辞不准确。
- 修复方向：文档改为「心跳过期（阈值 = 扫描周期×(N+1)）且一轮 IPC ping
  （内含 3 次探测）无响应即判挂死」。
