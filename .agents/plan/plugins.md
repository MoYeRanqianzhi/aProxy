# aProxy 插件（`[[plugin]]`）

**状态（2026-11-26）**：还只是一个想法，很多功能没定（用户 2026-11-26 原话：「插件现在还几乎是一个想法，很多功能没有定下」）。
0.2.0 之后做，版本未定。用户定了方向与六点（下一节）；待定的有：启动时检查三个问题（「启动时检查」一节末尾）、全局插件两件事
（「全局插件」一段末尾）、2026-11-26 补充的四项（「2026-11-26 用户补充」一节）。没有任务书，没有代码。

## 来由

用户 2026-11-23 受桌面扩展设计的启发：给 aproxy 本体也做扩展，不只是 format，而是完全强大的扩展——想要 TUI 可以做
TUI 插件，嫌 Tauri 慢可以换别的界面框架。核心想法是插件直接接 IPC 通讯，并在启动 aproxy 时运行某条命令。随后澄清：
插件不是自己去找实例的第三方客户端，而是在启动时就拿到相关信息；启动方式与 format 类似，但在后台，aproxy 不管它是否
持续运行，因为入口程序本身可能只是拉起插件自己的看门狗或后台服务。

## 用户定下的（2026-11-23）

1. **声明在 config.toml**：不同实例可能需要不同插件，所以跟着实例的配置走。全局的另见第 6 条。
2. **名字叫 plugin**，配置里是 `[[plugin]]`。与桌面窗口的扩展包（`kind: "extension"`、`<home>/desktop/extensions/`）是两种东西。
3. **安全靠启动时检查**：实例启动后一般只在关机时结束，或改了配置后 restart，所以可以在插件运行之前做一次基础扫描；
   用户也可以手动设一个参数，写上跳过检查的插件名。目的是不让未知插件被偷偷装上。
4. **用法接近 format**：不规定位置、语言、写法，完全自由。
5. **插件只管理声明了它的配置**（用户纠正主代理时说明）：有多少个配置注册了这个插件，插件就能使用多少个，不是默认管理
   全部配置。插件作为程序在技术上有全部权限，但规范是：没有安装这个插件的配置，插件不应该去管理，否则违背用户的意愿。
   主代理先前说「界面类插件管的是整个 home、所以倾向声明在 settings.json」，是理解错了。
6. **settings.json 可以声明全局插件**（用户补充）：相当于默认值，等效于每个 aproxy 配置里都写了一行这个插件。

## 设计草稿（主代理的建议，用户尚未逐条确认）

**全局插件（落实第 6 条）。** 不能放在 settings.json 的 `defaults` 下：`defaults` 是整键替换，配置里没写这个键才用默认值，
配置一写自己的 `[[plugin]]` 就把默认的整个取代了，与「每个配置都多一行」不同。所以单列一个键（名字实现时定），语义是追加：
每个实例实际的插件 = 全局插件 + 本配置的插件。由此：全局插件的管理范围是全部配置，包括以后新建的；启动时检查同样适用；
状态里的 `plugins[]` 注明每个插件来自 settings.json 还是配置。settings.json 也对不认识的键报错，写了这个键之后换回不认识它的
旧版本，所有命令都会因 settings.json 出错而停下（强制安装不读配置与 settings，不受影响）；给作者与用户的文档写明最低版本。
还要定两件事：配置里有同名插件时，以配置的为准（可以按实例改参数）还是报错；某个配置不想要某个全局插件时怎么排除。

**管理范围（落实第 5 条）。** 插件的范围是声明了它的那些配置，以及从这些配置启动的实例：
- 每次拉起都带着触发它的那个实例与配置（见下面的环境变量，含 `APROXY_CONFIG` 与 `APROXY_PLUGIN`）。入口幂等时的常见做法是：
  服务已在跑，就把这一次的实例信息交给服务再退出，服务由此知道自己被哪些配置注册。这是给作者的文档里要写的模式。
- 服务自己重启后要能重新得出范围：`aproxy status --json` 与状态快照里每个实例带上它的配置声明的插件（下面的 `plugins[]`），
  插件从中找出声明了自己的那些。按什么认出自己（条目名、解析后的命令路径）实现时定。
- 范围内的事：这些配置的实例的状态、停止、重启、请求历史、日志，以及改这些配置文件。范围外的事：别的配置与它们的实例，
  以及影响整个 home 的操作（安装与升级会滚动重启全部实例、`stop all`、settings.json 的全局默认）。
- 规范管不住程序本身的权限，所以这一条靠文档讲清楚、审查来查：插件去管没有声明它的配置，审查 skill 按不合规的危险信号处理，
  与扩展把数据写到自己的存储之外同等对待。

**配置条目。** `name`（在本配置内唯一；跳过检查、数据目录、日志都按它认）、`command`、`args`、`env`，解析规则与
`[[format]]` 相同：裸名先找 `<home>/bin/` 再找 PATH，相对路径相对 home。config.toml 对不认识的键一律报错、实例不启动
（有意如此，见 aproxy-cli skill 的 config-toml.md），所以写了 `[[plugin]]` 的配置在旧版本上起不来；给作者的文档写明最低版本。

**什么时候拉起。** 实例每次启动都把本配置的插件各拉起一次：普通启动、restore、看门狗重启、restart、升级时的滚动重启都算。
时机放在控制端点开始应答之后，插件一启动就能连上实例。拉起即走：不等它、不看退出码、不重启它、不登记台账（C3 只管 aproxy
自己的进程；是否开放看门狗守护待定，见「2026-11-26 用户补充」）。所以入口必须幂等（服务已在跑就不再起第二份），这一条写进给作者的文档。拉起失败、被检查拦下，都只记日志、进状态，
绝不影响实例启动与服务。

**交给插件的信息。** 后台拉起不留 stdin，没法像 format 那样握手，用环境变量：
- `APROXY_HOME`；`APROXY_EXE`：触发它的实例的可执行文件，插件调命令行用它，版本与实例一致，不会调到 PATH 里的另一个版本；
- `APROXY_VERSION`；`APROXY_IPC`：实例支持的控制协议版本，如 `1`；
- `APROXY_PLUGIN`：这个插件在该配置里的条目名；`APROXY_CONFIG`：声明它的配置文件的绝对路径（管理范围靠这两项认）；
- `APROXY_PORT`、`APROXY_INSTANCE_ID`、`APROXY_ENDPOINT`：控制端点名，插件不必照着 `aproxy-ipc/src/endpoint.rs` 自己算
  `home_id`（规范化路径再哈希，别的语言照抄容易在 subst 盘符与目录联接上算错）；
- `APROXY_DATA`：这个插件自己的数据目录。与待定的 `APROXY_FORMAT_DATA`（见 [w5e-extensions](w5e-extensions.md)）一起定命名与位置；
- 可选 `APROXY_REASON`：这一次是普通启动、restore、看门狗重启、restart 还是升级。
插件继承实例的环境（与 format 相同，`src/transform/pool.rs:811` 没有 `env_clear`），不另外交密钥。

**怎么拉起。** 复用 `spawn_detached_with`（`src/daemon.rs:613`）：不继承任何句柄、脱出作业对象、unix 上 setsid、标准流接空。
它拉起后不等子进程：从很快就退出的 `aproxy start` 里调用没问题，从常驻的实例里调用时，unix 上很快退出的入口程序会留成
僵尸进程，要另外回收。后台没有终端：TUI 只能由用户在终端里自己运行，插件入口拉起的是它的后台部分；图形界面在开机恢复这类
没有桌面会话的场合可能起不来，由插件自己处理。

**IPC 的兼容性够不够。** 机制够用：`v` 只在语义不兼容时递增，加 op、参数、字段、错误码、状态值都不递增，读者忽略不认识的
（`aproxy-ipc/src/wire.rs:200`）；快照里的 `ops` 与 `features` 供双方协商；`tests/contract_v0_2.rs`（控制协议与盘上记录）
和 `tests/json_docs.rs`（各命令的 `--json`）守着只增不改。要补的：
- 写明出了 v2 之后 v1 至少再支持多久。现在只规定了何时递增，没规定旧版本留多久；插件启动时拿到 `APROXY_IPC`，能自己降级，
  所以不必承诺永久。
- 插件的启动入口（何时调用、环境变量的名字与含义、`[[plugin]]` 的字段）是新的公开接口，同样只增不改，进契约测试。
- IPC 只管单个实例：状态、停止、请求历史、订阅（t10c 再加 format 重启与 control）。启动与重启实例、改配置、看日志在命令行
  一侧，插件用 `aproxy … --json`，两套都算公开接口。插件只对自己范围内的配置与实例用它们（见「管理范围」）。
- 每个实例至多 8 条订阅连接（`src/history.rs` 的 `MAX_SUBSCRIBERS`），插件多了要放宽。

## 启动时检查（方向已定，细节待定）

实例拉起插件之前先检查。检查不阻塞实例的启动与服务；被拦下的插件不运行，原因进实例日志、状态快照（新增可缺省的
`plugins[]`：本配置声明的每个插件，以及它已拉起、被拦及原因、拉起失败或跳过了检查）、`aproxy start` 的输出、
`aproxy doctor` 与桌面界面的实例页——开机恢复这类无人值守的启动里被拦，用户要能看到为什么插件没跑。按程序文件的指纹
缓存结果，没变的不重扫。

扫描的信号与 TODO 里「安全加固：安装时自动识别典型危险信号」共用一份，从三个审查 skill 的 `references/signals.md` 起步，
例如：命令行里的下载即执行与编码命令（`curl … | sh`、`powershell -enc`、`mshta`）、程序放在临时目录或下载目录、Windows 的
网络来源标记（Zone.Identifier）与 macOS 的隔离属性、参数里的脚本文件含混淆或 webhook 与隧道地址、读 config.toml 与
settings.json 里的 key、写开机自启。

检查的边界：home 里的任何记录，同一用户的程序都改得了，所以挡不住已经以用户身份运行的恶意程序。它挡的是替用户改配置的
agent 与脚本（包括被提示注入的 agent）和误操作，并让「跳过检查」成为显眼、可审查的一步。这与桌面扩展「防御只在安装前有效」
的思路一致（记忆 desktop-extension-trust）。

**待用户定的三个问题（主代理 2026-11-23 提出）：**
1. **跳过绑定什么。** 只认名字的话，换掉同名插件背后的程序就绕过了扫描。建议跳过记录同时绑定命令行与程序文件的哈希，变了
   就重新扫；跳过名单也不放在 config.toml，否则「加插件」和「加跳过」是同一次编辑。
2. **未知但看起来干净的插件。** 内容扫描认不出它。若要挡住一切未经用户同意加进来的插件，需要「首次出现确认一次」：新加的或
   变了的插件，用户确认一次之后才运行，确认时给出扫描结果。代价是每加一个插件多一步。
3. **format 有同样的口子。** format 程序同样在实例启动时由 aproxy 拉起，还看得到全部请求与密钥；只查插件，偷偷加一个
   `[[format]]` 就绕过去了。若把 format 也纳入检查，升级时已有的条目要自动视为已确认，否则升级后 required 的 format 被拦，
   请求全部失败（`format_unavailable`）。

## 2026-11-26 用户补充（都是待定，要权衡）

用户原话：「这个插件命令功能放到开发插件功能时一起实现。……比如插件可以决定配置，可以预设format，这样安装一个插件就能相当于
装了一套完整的预设format，并受到插件控制具体功能细节。插件可以接入IPC交互。还需要考虑插件是否应该允许开放看门狗守护，即插件的
后台守护程序可以通过注册的方式同样受到看门狗守护，需要考虑是否允许，需要权衡诸多问题」。

**插件命令（已定：随插件一起做）。** 例如插件让 `aproxy tui` 可用，而 `tui` 不在 `src/cli.rs` 的 `Commands` 里。主代理当时的分析
（建议，用户未逐条确认）：
- 倾向 git 与 cargo 的外部子命令约定：`aproxy foo` 找不到内置命令时，运行 `<home>/bin` 或 PATH 里的 `aproxy-foo`，交给它
  `APROXY_HOME` 等环境变量（与上面「交给插件的信息」一起定）；不另设配置登记，免得多一个要永久兼容的字段。若最终走插件声明，
  要定一个问题：`[[plugin]]` 跟着单个配置走，命令却是全局的，哪个配置的声明算数。
- 内置命令永远优先，任何插件都不能遮蔽内置命令；`install --force` 属于冻结契约 C1–C8，尤其不能被遮蔽。反过来，以后新增的内置
  命令会让同名插件命令悄悄失效，要给插件作者写明命名建议（例如带前缀），并让 `aproxy doctor` 能报出被遮蔽的插件命令。
- 安全：skill 教 agent 放心运行 `aproxy` 开头的命令，伪装成官方命令的插件命令更容易骗过 agent。`--help` 要把插件命令单列并标明
  第三方；它们要受启动时检查同样的约束；审查 skill 要加对应信号。
- 打错命令时的提示要从「没有这个命令」改成同时说明「也没找到插件命令 aproxy-xxx」；插件命令的 `--json` 与退出码不受我们约束，
  skill 要告诉 agent 这一点。

**插件决定配置、预设 format。** 装一个插件相当于装一整套预设的 `[[format]]`，具体行为由插件控制。要定的：
- 预设怎么进到配置：插件把条目写进 config.toml（用户看得见、能改，但插件在改用户的文件，删插件时要能干净撤掉），还是 aproxy
  加载配置时合并插件提供的条目（配置文件干净，但实际生效的配置不在文件里，`aproxy config show` 与桌面界面要标出每条来自哪个插件）。
- 与用户自己的 `[[format]]` 怎么排先后、同名时谁为准；插件删掉或被检查拦下时，它预设的 format 怎么处理（required 的 format
  缺了，请求会全部失败，`format_unavailable`）。
- 与「启动时检查」第 3 个问题连在一起：插件带进来的 format 程序同样看得到全部请求与密钥，必须同样受检查。
- 与第 5 条一致：只对声明了这个插件的配置生效。

**插件接入 IPC。** 方向与上面「IPC 的兼容性够不够」一致，用户再次确认。

**插件的后台守护程序能否注册给看门狗守护。** 现在的草稿是「拉起即走、不重启它、不登记台账」，这一条取决于这里的决定。看门狗是
每个 home 一个的全局看护进程（[watchdog-v1](watchdog-v1.md)），看护全部实例。要权衡的：
- 好处：插件作者不必自己写看门狗；重启、退避、开机恢复与实例一致；状态集中在 `aproxy status` 与桌面界面里。
- 代价：看门狗在「不间断」的关键路径上，接管第三方程序会把它的崩溃循环、挂死判定、资源占用带进看护进程；aproxy 会变成任意程序
  的常驻与开机自启通道，而审查 skill 把「写开机自启」当危险信号；进程台账（C3）现在只记 aproxy 自己的进程，记不记插件进程、强制
  安装停不停它们，牵涉冻结契约（只能加可选字段）；一个插件服务多个配置时，按哪个实例的生命周期来管。
- 主代理的倾向（未经用户确认）：先不开放。入口幂等，加上实例每次启动（含看门狗重启实例）都重拉一次插件入口，已覆盖「实例在、
  插件就在」的多数需求。若要开放，作为显式的选择（条目里写明要守护），限次退避，状态可见，受启动时检查约束；也可以只让看门狗
  定期重拉幂等的入口，而不去看护插件的进程本身，这样不进台账。
