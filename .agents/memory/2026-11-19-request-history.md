请求历史是数据面的旁路：记录最近 1000 个请求，并在 `history.body_budget_mb`（默认 64）之内整份保留体。
形状与规则在设计稿 [w2-contracts](../plan/w2-contracts.md) §6.3、§6.5、§6.7，给人看的说明在 `docs/architecture.md` 的
「请求历史」。这里只记代码与文档里看不出来的取舍和量法。

**体为什么拷贝。** 网络库（hyper）交出来的块是它读缓冲区的切片：缓冲区按「下一次读多大」分配（8 KiB 起，最大约
400 KiB），一次读没填满、下一次又要重新分配时，留住这一小片就留住了整个缓冲区——慢速的 SSE 响应每块几百字节，各占
8 KiB。`Bytes` 不暴露它背后的分配有多大，所以零拷贝留块就没法让「记在预算上的」等于「实际占的」。现在的做法：
自己拥有、大小正好的缓冲不拷贝（≤ 1 MiB 的请求体与重试重放共用一份；溢写之前攒的那 1 MiB 整块进历史），其余拷进
64 KiB 的块。要改成零拷贝，先解决记账，否则预算就不再是内存上限。

**量出来的开销**（2026-11-19，本机，loadgen 64 并发、2.1 MiB 请求体、约 300 KiB 响应；用线程 CPU 周期计数分段量）：

- 释放溢写前那 1 MiB 缓冲一次约 280 微秒 CPU（这么大的块分配器直接向系统要、直接还），占历史全部开销的三分之一。
  所以 1 MiB 的缓冲与 64 KiB 的块都有空闲表循环使用（各至多 8 MiB）。
- 为取 `model` 多打开一次落盘的请求体文件，每个请求约 3.4 毫秒墙钟（新建的文件再打开一次很慢，推测是安全软件
  扫描，没有证实）。所以 `model` 在溢写那一刻从内存里的开头一段读，读不到才开文件。
- 丢体时在记录表的锁里释放内存，会让每个新请求（`begin` 要这把锁）排队。释放挪到了锁外。
- 拷贝本身约每字节 1 个周期（目标块是冷的，本机压测时内存带宽是共用的）。这是剩下的主要开销，去不掉。
- 订阅连接一次只写一个事件时，64 并发下每秒只送得出一百多个（每写一次都要等运行时再排到这个任务），订阅者九成
  事件变成 `lagged`。现在把排着的事件合成一批一次写，同样的负载零丢失。

**Why:** B8 的验收阈值是「没有订阅者时吞吐不低于之前的 95%」。头一版实测只有 92–94%，上面几处是把它拉回来的改动；
哪一处都不是读代码能看出来的，都是量出来的。

**How to apply:**
- 量几个百分点的差别不要看单次吞吐：同一个二进制两次跑之间就差 5% 以上。与基线**交替**跑、多轮取平均，并同时
  记 aproxy 进程的 CPU 时间（`(Get-Process -Id <pid>).TotalProcessorTime`），CPU 时间两次之间只差约 1%。
- 找开销在哪：Windows 上没有现成的采样工具时，临时在可疑的函数里用 `QueryThreadCycleTime` 累计周期（kernel32，
  `-2` 是当前线程的伪句柄），退出时与 `QueryProcessCycleTime` 的总数一起打出来。墙钟计时会把等锁的时间算进去，
  会误导。量完删掉。
- 压测的三个程序在 `examples/`（`loadgen`、`mock_upstream`、`subscribe`），要用 release 构建；aproxy 跑在全新的临时
  `APROXY_HOME` 里、固定用不与用户实例冲突的端口，结束时只在那个 home 里 `stop`（见 [[protect-production-instances]]）。
  基线取要比较的那个提交单独构建一份。
- 往转发路径上加任何「每个请求做一次」的文件操作或大块分配之前，先想它在 Windows 上的价钱（毫秒级、几百微秒级）。
- 现在的余量很薄（平均 96% 对门槛 95%）：再往历史的热路径上加东西，要重新量。
- 看有没有泄漏用私有内存（`PrivateMemorySize64`），不要用工作集：机器上别的程序吃内存时工作集会被系统修剪
  （同一次长跑里从 33 MiB 掉到 22 MiB），涨落都不说明问题。

**Evidence:** 2026-11-19 与基线（提交 e433bee）交替压测七轮（各 30 秒）：基线 335–359 rps（平均 348），没有订阅者
328–340 rps（平均 334，为基线的 96.1%；单轮的比值 92.7%–100.7%），p99 平均 358 ms 对 348 ms；CPU 时间多 2.8%–4.4%。
长重试（上游拒绝连接、退避 0、8 并发、10 分钟）第 1 分钟之后常驻内存涨不到 3 MiB，最大的记录 5.3 KiB。完整数字与
逐项验收在 [release-0.2.0](../plan/release-0.2.0.md) 的 B8 条目。

**Recheck when:** 换了 hyper、bytes 或 tokio 的大版本（读缓冲的分配方式、`Bytes::from_owner` 的行为可能变）；默认
预算或 1 MiB 的内存驻留阈值改了（`RESIDENT_LIMIT` 与 `history::LARGE_BUFFER` 必须相等，有编译期断言）；换了机器或
系统后压测数字对不上。
