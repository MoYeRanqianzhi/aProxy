# 批评 ≠ 实施授权（2026-09-10 事故）

**What happened**: 我在 F2 总结里给出两个选项（都建立在名称判断上），
用户怒斥「怎么能通过名称来判断？严重谬误！」。我把这句批评当成实施授权，
未经对齐方案就直接开始跨文件重构（InstanceInfo 协议字段 + --force +
看门狗选举，两平台共享语义），被用户打断：「你真的在做 UNIX 修复吗？
为什么你改动了那么多其他地方的代码？」——改动越出了 fix/unix-first-test
分支「Windows 零行为变化」的验收承诺，最后全部回滚（稿存 stash）。

**Why**: 批评的语义是「你的方向错了」，正确响应是承认 + 给出修正后的
分析与方案，等确认再动手。且机制级替换（协议字段、平台共享行为）有
自己的边界：单平台修复分支不能夹带两平台语义变更；注册表/IPC 格式
变更与主仓在规划的 install 状态机可能交叉，需要显式权衡。

**How to apply**:
1. 用户批评/纠正后：先复述理解到的问题本质 + 提出修正方案，等用户
   确认；「严重谬误」级别的否定连方案都要重想，不是在原方案上小修
2. 动手前自问：这个改动的验收边界是什么（分支承诺/平台范围/协议面）？
   越界即升级为独立决策呈报，不夹带
3. 方向稿留存用 stash push -u 带唯一 message 并记录 SHA，不用裸
   git stash（多会话共享栈）
4. 既有语义（merge-base 前就有）不构成合理化依据——错的就是错的，
   「一直如此」恰恰可能是需要上报的设计债
