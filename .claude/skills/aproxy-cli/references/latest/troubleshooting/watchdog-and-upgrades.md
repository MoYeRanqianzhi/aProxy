# Troubleshooting: crash recovery, watchdog and upgrades

Part of [troubleshooting.md](../troubleshooting.md), which lists the other parts. Instances crash or are not brought back, or an install or upgrade fails.

## Crash recovery, watchdog and upgrades

| Symptom | Cause | Fix |
|---|---|---|
| An instance came back after it was killed | It was killed by PID (or crashed), so its desired-state record stayed and the watchdog respawned it | Stop instances with `aproxy stop <port>`, or `--force` if hung |
| After a crash, an instance came back with different settings or on another port | A respawn starts from the saved launch spec but reads the config file as it is now; a port-0 instance returns to its pinned port unless the config names a fixed one | Keep config.toml in the state you want running; apply edits with `aproxy restart` instead of leaving them pending |
| A crashed instance stays down; startup.log has `[watchdog] the instance on port <port> failed to come back N times in a row; retrying every 300 seconds until it starts or aproxy stop <port> is run` | Crash loop: the fast respawns failed, so the watchdog switched to one retry every 300 s. It does not give up | Fix the cause shown earlier in startup.log. The watchdog keeps retrying; `aproxy restore` tries immediately. To give up on the instance, `aproxy stop <port>` removes its record. With `watchdog.max_restarts = 0` the watchdog never retries automatically and only `aproxy restore` does |
| Is the watchdog running? | No `Watchdog:` line at the end of `aproxy status`, or one saying "no scan for ..." | The line shows its PID and the time since its last scan; `<home>/run/watchdog.json` has the same facts and `<home>/logs/watchdog.log` lists what it did. Instance logs show "Watchdog was absent; this instance won the election and started it" when an instance relaunched it. It is off when settings.json has `watchdog.enabled: false`, and unsupported on macOS. Setting that to `false` makes a running watchdog exit at its next scan; `aproxy start` launches it if absent, and instances check every 5 minutes |
| Instances are not back after a reboot | The watchdog does not survive a reboot; the desired-state records do | `aproxy restore`; register it as a logon task to make this automatic |
| `aproxy restore` reports `端口 N 恢复失败：新实例（pid P）启动后立即退出…` or `…未在预期时间内就绪…` ("exited right after start" / "not ready in time") | Config error, bind failure, or slow start. The record is kept | Read `<home>/logs/startup.log` |
| `aproxy restore` prints `端口 N 的配置文件找不到（…），这次没有恢复；记录已保留…` | The config file is temporarily absent (a network or removable drive that is not mounted) | Bring the file back and run `aproxy restore` again. If the instance is no longer wanted, `aproxy stop N` deletes the record |
| `aproxy restore` prints `跳过读不懂的记录 <path>: …` | The record is damaged or was written by a newer aProxy | Leave it for the version that wrote it, or remove it by hand once it is obsolete. Readers never delete it; `aproxy stop <port>` does delete the record of that port without reading it |
| A port still answers requests but `aproxy status` lists nothing there and `aproxy stop <port>` says `端口 N 上没有运行中的 aProxy 实例。`; `run/<port>.pid` or `run/<port>.restore` exists | The instance was started by 0.2.0-alpha.1/alpha.2, whose records and status snapshot this version cannot read | compatibility.md, "Upgrading from 0.2.0-alpha.1 or 0.2.0-alpha.2": `aproxy install --force` ends such processes, then start each instance again |
| `aproxy status` shows `二进制更换中（install 滚动重启阶段，请勿手动干预此实例）` ("binary swap in progress; do not intervene") | `aproxy install` is mid-rollout | Leave the instance alone until install finishes |
| Install aborts with `实例未表达（已按重试/restart 收敛）` or `实例 <port> 收敛重启失败` | That instance did not enter the swap phase even after restarts | Ask the user whether it may be stopped; stop it and run `aproxy install` again |
| Install exits non-zero with `滚动已中止，不会自动重试：…` ("rollout halted, will not retry") | The new version could not start an instance; it was brought back on the old binary | `last_error` in `<home>/install/state.json` and startup.log give the reason (often stricter validation of an existing config); fix it and run `aproxy install` again |
| `aproxy install` on 0.1.x exits 1 with an `[ERROR]` line containing `--version 输出无版本号: "aproxy v…` ("no version number in the --version output"), possibly followed by download-proxy advice | 0.1.x cannot install 0.2.0 or later and stops before changing anything; the download itself worked | Reinstall instead: compatibility.md, "Moving from 0.1.x to 0.2.0" |
| `目标版本 <v> 低于 0.2.0，不能安装：…` ("target version below 0.2.0 cannot be installed") | 0.2.0 and later never install 0.1.x, even with `--allow-downgrade` or `--from` | compatibility.md, "Going back to 0.1.x" |
| `aproxy status` notes `注意: 实例版本 vX 与当前 CLI vY 不同，…` ("instance version differs from the CLI") | That instance still runs an older binary | `aproxy restart <port>` moves it to the installed version; it cuts in-flight requests, so confirm the instance is idle or the user agrees |
| `aproxy install` keeps failing or hangs, or `aproxy` no longer runs at all | The hand-over or the rollout cannot complete, or the installed binary is broken | Force install (commands.md, Force install): `aproxy install --force`, or with a broken binary `<downloaded release binary> install --force --from <that file> --yes`. It cuts every request in flight through aProxy, your own session's included, so get the user's agreement first |
| `aproxy install --force` exits 10 | No process was stopped and the binary was not replaced: the home does not exist (a mistyped `APROXY_HOME`), the download, checksum or `--version` check failed, the target is below 0.2.0 or of another variant, `latest` resolved below the running version, the release has no build of the requested variant or CPU level for this platform (the error ends with `这个目标只有 …`, "this target only has …"), there was no confirmation (stdin is not a terminal and `--yes` is missing), or a later step failed before any process was stopped | Fix what the `[ERROR]` line names; pick a variant and CPU level from the listed ones. On Linux without WebKitGTK, add `--variant headless`. Add `--yes` only after the user agreed |
| `aproxy install --force` exits 11 | At least one process was stopped but the binary was not replaced: another process holds the install lock or the binary file, a process could not be stopped (for example one running as administrator), or a write failed | Fix the reported cause and run the same command again; or run `aproxy restore` to bring the instances back on the old binary |
| `aproxy install --force` exits 12 | The binary was replaced; the instances it lists did not come back | Run the command printed for each (`aproxy start --config "<path>"`); `<home>/logs/startup.log` has the reason |
| `aproxy install --force` exits 1 or 137 | Another force install on the same home started later and stopped this one | Read the later run's exit code instead |
| Force install lists processes under `…但不在台账里…` ("…but not in the ledger") | They run from `<home>/bin/` but keep no ledger (0.1.x), so force install left them running | Stop them with the 0.1.x CLI (compatibility.md, "Moving from 0.1.x to 0.2.0") |
