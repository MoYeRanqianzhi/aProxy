2026-08-28 实测：上游 `https://xn--wnup5g6so4wn.de5.net` 经 aProxy 出现 502 回透到客户端。

错误归因（已推翻）：曾误判为 `reqwest` 未启用 `system-proxy`/`socks` 导致不走 `127.0.0.1:7890` 直连失败。推翻理由：若外发代理不通，`reqwest::Client::builder().send().await` 会返回 `Err`，进入 `proxy.rs:ForwardResult::NetworkError` 并在 `proxy_handler` 的 `loop` 中无限重试（梯度延迟 0/0/0/5s…320s），客户端现象应为长时间挂起而非立即收到 502。因此 502 回透证明已收到上游响应但未被重试逻辑拦截。

真实方向：502 已落在 `is_retryable_status` 判定或 `is_error_body`/`is_stream_error_body` 覆盖之外，或重试循环被旁路/未生效。当前 `retry.rs:is_retryable_status` 已为 `400..=599`（包含 502），`proxy.rs` 中对 `is_retryable_status` 为真即 `continue`，按设计不应回透。

**Why:** 之前的排查把“能 curl 通 7890”当成“reqwest 必须走 7890”，忽略了无限重试语义对故障现象的约束，导致排查偏离。

**How to apply:** 
- 不再以“补 system-proxy 特性”为 502 的修复；是否走系统代理属后续“可配置代理”功能，当前仅作外部环境验证手段。
- 聚焦核实：`proxy.rs` 的 `is_retryable_status` 是否真实命中 502、`body` 预览是否被错误判定为非重试、以及 release 二进制是否为最新构建（`cargo build --release` 后是否已重启生效）；必要时在 `proxy_handler` 中对 502 分支打 `tracing::warn` 并复测 `curl -v http://127.0.0.1:8040/<path>` 对比直连 `https://xn--wnup5g6so4wn.de5.net/<same-path>` 的状态与 `content-type`/`body` 差异。
