用户 2026-10-11 定下 0.2.0 的方向：

- **去掉全部兼容，包括 0.1.0 的原地升级兼容**（`src/compat_0_1_0.rs` 的 S1–S5、install 的 relaying 豁免、
  `tests/compat_v0_1_0.rs`、CI 的 upgrade-from-0-1-0 任务）。0.1.0 用户重新安装。
- **前瞻性与稳定性优先**：用户极少，这是去兼容、改契约最好也是最后的廉价时机；0.2.0 之后对外接口要长期稳定。
- **0.1.0 的内容不默认优秀**：此前的模型较弱，留下不少问题；要有自己的判断，允许大规模重构。
- **文本语言**：给用户看的（命令行输出、`--help`、UI）做 i18n，随语言环境切换（en / zh-CN）；给 agent 看的
  或用户看不见的（日志、发给 HTTP 客户端的错误体与流终态事件、IPC 线上文本、信封 error、skill、`--help`
  末尾的 skill 提示行）固定英文。
- **代码注释、CHANGELOG、docs、`.agents` 记录保持中文**，不改。
- **UI 是 Tauri 2，编进 aproxy 本体，默认启用**；用条件编译（cargo feature）另出无 UI 版本。这推翻了
  10-04 审查「独立二进制」的建议。**所有平台都发两个版本**（带 UI / 无 UI），现有每个二进制产物都翻倍，
  aarch64 Linux 也不例外；**例外是 musl 只出无 UI 版**（用户 2026-10-12 定：musl 带 UI 版只能动态链接、只能跑在装了
  webkit 的 musl 发行版上，失去 musl 版的意义），共 20 个产物。**Linux 上自动选择变体**（用户 2026-10-12 定）：
  带 UI 版缺 webkit2gtk 时连 `--version` 都起不来，所以安装脚本与安装器探测到库才装带 UI 版，否则装 headless 并说明。
  启动方式是 `aproxy desktop`。无 UI 版本叫 headless（npm
  `@meowo/aproxy-headless`、资产 `aproxy-headless-<target>`），带 UI 的沿用现有名字。用户已有的两个 skill（tauri-custom-titlebar、tauri-windows-mica）的做法
  要用上；Mica 默认关闭，在 UI 设置里开启，要考虑没有 Mica 的 Windows 11。
- **界面可高度自定义**：主题、吉祥物（按状态渲染、内置几种、可选、用户可注入，也可作软件图标）、扩展；完整注入
  作为正式功能提供，权限按扩展声明分级（装饰级隔离、完整权限级启用时确认）；用法做成 skill。细节在计划 W5。
- **安全边界在实例与 IPC**：UI 只是 UI，不持有 key、不经手流量；IPC 不返回明文密钥，UI 的 webview 不联网，扩展只在
  「写」操作上需要用户同意（用户 2026-10-11 纠正了主代理「UI 拿着 key」的错误说法）。
- **新增 `install --force`**：更新失败时的兜底——强制关掉进程再安装新版本，不走交接，保证以后兼容怎么改都能装上。
- **契约决策（2026-10-11）**：重试配置改为规则表；`config`/`settings` 用 get/set/unset，`--baseurl` 改 `--base-url`；
  请求侧转换失败由 format 在回信里用约定结构声明是否重试并可自带给客户端的响应（不靠错误码）；裸 `aproxy` 只输出
  帮助。细节在计划 W2 的用户决策一节。
- **审查后的契约决策（2026-10-12）**：默认无限重试不变；等多久、要不要停以 format 的结构化指令为主，aproxy 不读 Retry-After、
  不加抖动（不信上游）；同一 format 程序连续进程级失败就熔断（required 的请求快速失败）；请求历史在内存里保留全部请求的体，
  总量上限有默认值、可配置；config.toml 与 settings.json 里不认识的键一律报错，不为 0.1.x 旧键写任何提示代码；settings
  的全局默认为方便而设，可以放上游地址、key 与代理（listen_addr 除外），头表按名合并，但凭据只发给它所属的上游或代理。
  细节在计划 W2 的「审查后的用户决策」（D-12…D-16）。
- **新增 `aproxy skill` 命令**：只下载 skill 的 `skill install/upgrade`，能直接用命令查看 skill 内容（给
  读不了目录的 agent），不能被借来读别的文件；本地没有 skill 就提示，不把 skill 嵌进二进制；`--help`
  末尾加一行提示 agent 有 skill 可看。细节在计划里。

**Why:** 以上是用户的产品决策，不是推导出来的；理由就是上面每条后半句。

**How to apply:** 0.2.0 期间改任何对外可见的东西（IPC、磁盘布局、config/settings 字段、CLI、HTTP 错误体、
信封）都按「之后冻结」来设计，不再为 0.1.0 留读旧逻辑；新写的字符串先判断给谁看，再决定 i18n 还是固定英文；
UI 相关一律走 `desktop` feature（默认开启，`--no-default-features` 出 headless），无 UI 版本不能因此多出任何依赖。

**Evidence:** 用户 2026-10-11 原话：「去掉兼容后直接开始发0.2.0，这个版本同时开始加入UI……当前用户极少，
是最佳的去除兼容时机……必须要有前瞻性、稳定性的设计。给用户的需要i18n，给agent的或者不可见的固定英文」；
「1的改版，tauri放在本体中，默认内置，通过条件编译额外编译无UI版本」；「所有平台都要发两个版本，即当前二进制数量翻倍」；「启动方式设计为 aproxy desktop」；转换失败：「不能返回错误码，因为任何错误码都是必须重试的，改成约定的内容，这样aproxy就知道这是转换器的问题，并且还能知道这个问题是否应该重试（带在返回信息中）」；「实际理论上用户本身就可以做到注入，这是tauri天然具备的问题」「可以，后续并将其用法做成skill……具体自行实现」；「aproxy的ui只是ui而已，实际看不到任何东西，敏感内容全在aproxy其他实例中」；「新增一个功能，强制更新--force，如果更新失败可以使用强制更新，相当于强制关掉进程，然后安装新版本，无交接过程」；「读取两个tauri skill，使用其中
技术。其中mica作为可选，默认不启用，但是可以在ui设置中启用。需考虑win11无mica」。2026-10-12 用户在选择题里选定
Linux「自动选择变体」与「musl 只出 headless」（依据计划附件 tauri-embedding-research 的调研）。

**Recheck when:** 用户改变以上任一方向；0.2.0 发布后（此条转为历史，永久接口另记）。
