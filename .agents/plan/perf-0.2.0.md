# 0.2.0 的性能：基线、重测与优化

状态：基线测量进行中（2026-11-20 启动，任务 p01）。任务的先后与分工见 [codex-tasks-0.2.0](codex-tasks-0.2.0.md)。

## 为什么做

用户 2026-11-20：在服务器上运行最新的 aproxy 并评估性能，包括启动速度、静默时占用的内存与 CPU、低并发与高并发时的占用、
延迟，严格测算；后续功能都接入之后有性能优化环节。

现有的数字都旧了，也都是在 Windows 上测的：`docs/benchmark-memory.md`（2026-09-07）与 `docs/benchmark-watchdog.md`
（2026-09-08）早于 0.2.0 的 IPC v1、请求历史、统计计数器与 format 协议 1。B6 当时就记下：每个请求、每次重试各锁一次统计
用的互斥锁，没有压测过它对吞吐的影响。

## 三步

1. **基线（p01，现在）**：对 `v0.2.0-alpha.3` 的发布构建（headless、x86_64 linux gnu，另测 `-v3`）与 `v0.1.0` 测同一套场景。
   0.1.0 是现在生产上跑的版本，用来回答「0.2.0 有没有变慢、变重」。
2. **重测（p02，beta.1 之后）**：功能都接入之后，用同一套脚本对 beta.1 的构建重跑，同基线逐项对比；加上 format 链的场景
   （官方 aproxy-format 的各个角色、spawn 与 persistent、不同的 `request_body` 粒度）。
3. **优化（t12，rc.1 之前）**：依据前两步的发现逐项做。每一项：先有一个说明问题的测量（能重跑、数字稳定），再改，再用同一个
   测量证明改善，并确认别的场景没有变差。没有测量支持的改动不做。优化之后的数字写进 `docs/` 的新基准文档，旧的两份
   随之更新或删除。

## 在哪里测

用户指定的一台 Linux 服务器：KVM 虚拟机，2 个 vCPU（同一个物理核的两个线程），内存约 1.7 GiB，Ubuntu 24.04，内核 6.8，
cgroup v2，有 Docker。它同时跑着用户的生产服务，其中有 aproxy 0.1.0 的生产实例。怎么连它、上面具体有什么，是这台机器
自己的事，不写在随仓库走的记录里。

所以有两条铁则，写在 p01 的任务书里，以后的性能任务照抄：

- **不碰生产实例**：不读、不写生产实例的 home（里面的配置有 API key），不运行那里的二进制，不按名字结束进程，不改主机的
  任何设置。每组场景之后核对生产进程的 pid 与运行时长，变了就立刻停下。
- **测量只在自己建的 Docker 容器里做**（名字以 `aproxy-bench-` 开头，没有网络，有内存上限，独立的 PID 命名空间）。原因：
  0.1.0 的控制端点与看门狗不按 home 隔离，在主机上再起一个 0.1.0 可能影响生产实例；容器让这件事不可能发生。

这台机器很小、又是虚拟机，数字的绝对值不代表别的机器。要的是：同一台机器上两个版本的相对关系、各场景的形状（哪里是
拐点、哪里线性增长），以及找出时间与内存花在哪里。

## 测什么（p01 的场景）

| 场景 | 内容 |
|---|---|
| S1 启动 | `--version` 的进程启动（冷、热）、前台启动到第一个请求成功、`start` 命令返回、`status`、`stop`、`restart` 的耗时、二进制大小 |
| S2 静默 | 一个实例空闲 10 分钟的内存（RSS、PSS、私有）、CPU、唤醒次数、磁盘写；三个实例；服务过 1000 个请求之后 |
| S3 低并发 | 1、4、8 路在途，三种负载：吞吐、延迟、每请求的 CPU、每个在途请求的内存与磁盘 |
| S4 高并发 | 容量曲线与拐点；重负载下一直加到内存上限或出错，记下出错时客户端看到什么、实例是否存活与恢复 |
| S5 延迟 | 固定到达速率（容量的 10%、50%、80%），修正 coordinated omission，p50 到 p99.9，首字节与末字节分开 |
| S6 重试态 | 上游持续出错 120 秒再恢复：等待中的请求各占多少内存与磁盘、aproxy 的 CPU、重试的次数与间隔、保活的间隔与抖动、恢复之后多久全部交付 |
| S7 长跑 | 30 分钟：内存与文件描述符随时间的斜率、延迟是否漂移、停止负载之后归还多少 |
| S8 时间花在哪 | CPU 剖析（perf）与系统调用的构成 |

三种负载：`small`（1 KiB 请求与响应，测代理自身的开销）、`chat`（64 KiB 请求、约 4 秒的流式响应）、`heavy`（2.1 MiB 请求、
5 万条事件，沿用 benchmark-memory 的画像）。

**严格的含义**（任务书 §3）：每个数据点至少 5 次、启动类 30 次，报中位数、最小最大与变异系数；两个版本交替跑；有请求失败
或字节不对的那一次不出性能数字，出一条发现；每个负载场景另跑一次「直连 mock 上游」，证明测量工具不是瓶颈；记录 steal
与生产进程的 CPU，噪声大的重跑；原始数据全部保留，报告里的每个数字都能追到原始文件。

## 基线

p01 于 2026-11-19 到 21 日做完（Codex，gpt-6.2-sol）。被测的是**发布的可执行文件**：A 为 0.2.0-alpha.3 headless（GNU 基线），
B 为 0.1.0；都没有挂 format。八组场景共 1252 次试验，995 次有效。完整报告、脚本、原始数据与三张图在本机的
`.agents/codex.local/p01-work/`（`report.md`），服务器上另有一份。每格是中位数，方括号里是最小到最大。

**测量条件的限制（读下面的数字之前先看）**：
- 测量在一台与生产实例共用的小机器上、内存上限 900 MiB 的容器里做；压测工具、mock 上游与被测实例共用 CPU。
  高并发下 mock 直连自己也到了极限，所以吞吐是「整套环境」的数，不是代理本身的上限。
- S3、S4 按时间预算削减过：只测钉核的摆放，S4 只测 forward；S5 只测 50% 与 80% 两档，而且 A、B 各按自己的峰值取
  比例，**两者的施加速率不同**，不能直接比。
- 可执行文件去掉了符号，S8 的 CPU 剖析有 82% 到 83% 归不到函数上，定不了热点。

小请求 80% 档，**A 十次里九次被容器的内存上限杀掉**，B 六次里一次（施加速率不同，见上面的限制）。对话 80% 档两边都在 4 秒上下，无差别。

**上游中断 120 秒（S6）**：两个版本合计 800 个在等的客户端全部拿到了完整、正确的响应；上游恢复之后 37 到 39 秒全部完成，
与退避一致。A 每个在等的大请求占的内存是 B 的 2.07 到 2.20 倍。

**长时间运行（S7，只测了 A）**：负载停下之后文件描述符回落到 13，但留着约 192 MiB 的 PSS 与 63.5 MiB 的磁盘；
拟合的 20 分钟里 PSS 上升约 1.55 MiB。这些数分不清是泄漏还是请求历史。

**一句话**：0.2.0 的启动与命令快了很多；**处理请求变贵了**（小请求 CPU 多三成、吞吐少两成），**占的内存多了很多**
（跑过请求之后 5.7 倍、大请求在途时 3.6 倍），小请求高负载下更容易撞上内存上限。这些都是 0.2.0 相对 0.1.0 的退化，
最可能的来源是请求历史（0.2.0 新加，默认开）与重试缓冲，但 p01 没有把它们分开，下面列为假设。

## 重测（p02，进行中）

2026-11-27 派出，同一台服务器、同一套脚本与镜像。A′ 为 0.2.0-beta.1 headless（GNU 基线），A3′ 为它的 `-v3`；
另重跑 alpha.3 的 S1 与 S3 一点作漂移对照（没有超出阈值的漂移，只有 retry 的 p99 高了 10.3%，范围重叠），所以下面
「alpha.3」指同期重跑的 A。截至 2026-11-28，S1 到 S6 与历史预算两组做完并审核，S9（format）、S8（带符号的剖析）、
S7 还在跑。报告草稿在本机 `.agents/codex.local/p02-work/report.md`。

中期结果（测到的事实；括号里是证据所在）：

- **大请求的 forward 退化（beta.1 新出现）**：heavy 32 并发，每请求 CPU 108 毫秒、8.7 请求/秒；alpha.3 是 10.7 毫秒、
  21.0 请求/秒；直连对照没变（21.5）。retry 一直是这个量级（8 并发：beta.1 133、alpha.3 138、0.1.0 108 毫秒）。
  beta.1 给 forward 加了被动的错误检查，走的正是 retry 用的那个行扫描器，所以开销来自扫描器的推断很强，但还没有测到
  归属（`raw/preflight/S4-beta-analysis.md`）。扫描器按代码看有两处贵：每取一行就把缓冲区剩下的部分整体前移
  （一块里行越多越接近平方），每条 `data:` 事件都整块解析成 JSON 树。已派 t28 修。
- **高负载下内存超限仍在，与请求历史无关**：同一施加速率（小请求 5590 请求/秒）下 beta.1 与 alpha.3 都六次全被杀，
  直连全过；把历史预算设成 0 也五次全被杀。出错时压测端 4096 个在途全占满（`raw/preflight/S5-history-analysis.md`）。
- **跑过请求之后留着的内存，主要是请求历史的体**：1000 轮对话之后空闲，历史预算 64、16、0 MiB 时实例 PSS 是
  83.8、35.0、18.1 MiB，三组范围不相交。默认 64 MiB；改成 16 MiB 省约 49 MiB，代价是能回看的响应体少（要定）。
- **小请求的 CPU 比 alpha.3 又多了一点**：钉核 4 并发 retry，每请求 157.9 微秒（alpha.3 149.0、0.1.0 118.2），吞吐少
  6.6%，范围不重叠。等 S8 的剖析定热点。
- **前台启动**：retry 中位数比 alpha.3 慢 19.8%（29.5 对 24.7 毫秒），范围重叠；后台启动 110 毫秒，与 alpha.3 相同。
- **v3 构建的启动异常又出现一次**：A3′ forward 41 次里一次，监听报告就绪之后 TCP connect 超时，与 p01 同一阶段，仍未归因。

## 发现与优化候选

（p01、p02 的发现按对用户的影响排序列在这里；每条写明证据在哪、是测到的事实还是假设、打算怎么验证。）

- **高负载下内存超限（最要紧）**。事实：S5 小请求 80% 档，A 十次里九次被容器 900 MiB 的上限杀掉，受影响的每次试验
  压测端都记到 4096 个客户端失败；B 六次里一次。直连对照都通过。限制：A、B 的施加速率不同。证据：报告的 S5 一节与
  `raw/S5/`。假设：retry 模式下在途请求的缓冲加上请求历史，没有一个按总量的上限，负载一高内存先于吞吐到头。
  验证：两个版本在**同一个施加速率**下重跑小请求的开环曲线，出错之前记下在途数与实例的 PSS；再把请求历史关掉重跑，
  看差多少。目标是同样的速率下不再有失败与截断，而不是更高的瞬时吞吐。
- **跑过请求之后留着的内存**。事实：1000 轮对话之后空闲，A 是 84.78 MiB、B 是 14.83 MiB；S7 停下负载后仍留着约
  192 MiB。假设：大部分是请求历史按设计留着的记录与体（有上限，见设计稿 §6），不是泄漏；20 分钟里 1.55 MiB 的上升
  要另查。验证：用不同的历史预算（含关掉）重跑 S2 的负载后空闲与 S7，看稳态 PSS、斜率与磁盘占用。若确是历史，
  要定的是默认预算合不合适，以及文档里要不要写明内存占用。
- **每个请求的 CPU 多了约三成**。事实：钉核小请求 4 并发，A 每个请求 153.8 微秒、B 118.2 微秒，吞吐少 19.1%，
  p99 高 37.2%，各次重复的范围不重叠；大请求每个多 26.9%。S8 看到 futex 占系统调用时间的 72% 到 75%、
  分配约占 5%，但符号被去掉了，定不了热点。验证：先出一个同样优化级别、带符号的构建（核对 build-id），
  在同样的在途数下比 retry 与 forward，看每字节的 CPU、落盘的写与复制次数；任何改动都用不带跟踪的脚本复测。
- **大请求在途时的内存**。事实：大请求 8 并发时 A 的稳态 PSS 是 B 的 3.6 倍；S4 里 A 不出错的最高并发是 B 的一半；
  S6 里每个在等的大请求占 B 的两倍多。假设：0.2.0 对同一个体留了不止一份（重试缓冲、历史、打码扫描）。
  验证同上一条，另看落盘阈值是否生效。
- **一次没有复现的启动异常**。事实：S1 里 A3（x86-64-v3 构建）有一次前台启动之后，探测在 TCP connect 上超时，
  而监听已经报告就绪、进程一直活着（`raw/S1/s1-a3-retry-073/`）。没有复现，没有归因。记下，再出现时对照。
- **启动快了的原因**（不是问题，记下以免以后改回去）。0.1.0 在检查端点不存在时先睡两次 200 毫秒再绑定；0.2.0 只对
  瞬时的 IPC 错误重试。

- **挂了 format 之后的吞吐（B10d 的验收，没过线，待重测）**。测到的事实：开发机上 64 并发、每轮 30 秒、三轮交替，
  挂一个从不读 stdin 的 notify 程序时吞吐是无 format 对照的 94.3%、p99 是 110.4%；只要摘要的 request、decide、notify 链
  是 90.9% 与 102.6%。门槛是 95% 与 110%。限制：对照自己在三轮之间从 226 变到 346 请求/秒，机器当时内存很紧，
  差距在噪声之内，不能据此说有或没有退化。数字在[发版计划](release-0.2.0.md)的 B10d 一条里。
  打算：p02 在服务器上加这两种链形状各一个场景，与无 format 的同版本对照；确有退化再归 t12。
