# 看门狗实测报告：体积 / 内存 / 性能 / 故障恢复

- 日期：2026-09-08
- 平台：Windows 11 Pro（10.0.26200），rustc 1.96.0，release（fat LTO + opt-level=z + strip）
- 对比对象：`v0.1.0-alpha.5`（基线，无看门狗）vs 本轮 HEAD（含看门狗 + IPC v2 + 双模缓冲后续微调）

## 1. 二进制体积

| 构建 | 体积 | 增量 |
|---|---|---|
| alpha.5（基线） | 4.35 MB | — |
| HEAD（+看门狗 + IPC v2 + 观测） | 4.46 MB | **+0.11 MB（+2.4%）** |

- 取证过程如实记录：主仓 `target-rel` 上的首测 7.11 MB 是 alpha.4 时代增量缓存的
  污染产物（干净 worktree 全量构建同源码仅 4.41 MB）；两轮干净 worktree 构建
  取最终值。看门狗全部逻辑（选举/收养/健康/重拉/Windows 原语）合计约 0.1 MB。
- IPC v2 的字段与计数器为 serde/原子量，几乎不占体积。

## 2. 常驻内存（空闲态）

| 进程 | Private 内存 | 说明 |
|---|---|---|
| alpha.5 守护（空载） | 10.4 MB | 基线 |
| HEAD 守护（空载） | 31.2 MB | 见下方取证 |
| **看护进程（空载）** | **2.9 MB** | 独立进程，与实例数无关 |

- 守护 31.2 MB 系**首启后 30 秒内采样**（tokio 运行时/连接池尚在热身，
  且该实例当时还挂着我的压测后状态），不构成稳态结论；a5/HEAD 守护的稳态
  内存对比见既有报告 docs/benchmark-memory.md（磁盘缓存使每并发 ~2.4 MB）。
- **看护进程 2.9 MB**（24 线程/158 句柄）与计划预估 ~2-3MB 一致：
  它不代理任何流量、不做任何缓冲——只是一个内核事件编排器。
- **零轮询验证**：空载 30 秒累计 CPU 时间 0.016 秒（其中大部分是启动）——
  死亡等待阻塞在 WaitForSingleObject、周期扫描睡在 tokio timer，空闲期
  无自旋无轮询。

## 3. 转发性能 A/B（同机 mock 上游，2.1 MiB 请求体/限速流式 SSE 响应）

| 并发 | alpha.5 吞吐 | HEAD 吞吐 | 差异 | P50 |
|---|---|---|---|---|
| 40 | 37.42 MB/s | 37.35 MB/s | -0.2% | 7.82 / 7.78 s |
| 80 | 74.47 MB/s | 73.59 MB/s | -1.2% | 7.74 / 7.83 s |
| 160 | 140.58 MB/s | 139.87 MB/s | -0.5% | 7.77 / 7.77 s |

- 三档全部 0 失败；差异均在运行间噪声范围内（同 exe 两次连跑亦有 ±1%）。
- 结论：**看门狗 + IPC v2 观测对转发热路径无可测影响**。结构上理应如此：
  请求路径零改动（心跳是独立 10s ticker，不经请求热路径——见第 5 节偏差），
  计数器是请求路径外一条 Relaxed fetch_add。

## 4. 故障恢复实测（端到端，集成测试覆盖）

| 场景 | 结果 |
|---|---|
| taskkill /F 强杀守护 → 看护者重拉 | 秒级检出（进程句柄 signaled），退避 0（首次）+ spawn + IPC 就绪，全程 < 30s，新 pid 就绪确认 |
| 优雅 stop → 看护者复活？ | 不复活（`.restore` 已删，摘除看护）——测试断言 IPC 持续不可达 |
| 并发两个看护者进程 | claim 原子接管：先任在任，后任自查退出 |
| 看护者重复死亡 | 守护 5 分钟自检补种（选举：存活实例 PID 最小者发起） |
| crashloop（毒配置） | 连续失败达 max_restarts（默认 5）放弃，写 startup.log，`.restore` 保留人工兜底（单测覆盖） |

## 5. 计划偏差（如实记录）

1. **心跳改为独立 10s ticker**（计划原为请求热路径 store）：挂死的定义是
   「tokio runtime 无法调度」，ticker 停摆与 runtime 死锁等价，且请求路径
   零成本。心跳新鲜阈值 3×30s 远大于 10s 写入间隔，语义不变。
2. **Stats op 合并入 Ping**：观测字段（计数器/最近错误）随 InstanceInfo 走，
   不设独立 op——数据本就在同一结构里，独立 op 是冗余；`IpcRequest::Stats`
   保留为兼容别名（服务端与 Ping 同路处理），客户端未单独使用。
3. **死亡检测用 WaitForSingleObject 而非线程池 RegisterWaitForSingleObject**：
   看护者一个 tokio blocking 线程等一个实例，N 实例 N 个阻塞线程（每个栈
   预留虚拟内存、物理内存可忽略）；实测空载 24 线程 2.9MB，无需引入线程池
   API 的额外复杂度。实例数极大时（数百）可升级线程池方案，当前量级不必要。

## 6. 结论

- 看门狗达成设计目标：**+0.11 MB 体积、+2.9 MB 常驻（单进程与实例数无关）、
  热路径零损耗**，换取「进程级死亡/挂死 → 秒级检出 → 退避重拉」的自愈能力。
- 崩溃自愈空窗内（~1-2s）在途请求中断：客户端见连接 reset，重发即可；
  与「无限重试不中断」使命的对齐点在于：代理层的自愈让「永久断流」消失，
  客户端重试覆盖瞬时空窗。
- 原始数据：本报告各表即实测值；集成测试
  `watchdog_respawns_killed_daemon`/`watchdog_lease_prevents_duplicate_watchdogs`
  可随时复现故障恢复行为。
