# Troubleshooting: starting and stopping

Part of [troubleshooting.md](../troubleshooting.md), which lists the other parts. An instance will not start, will not stop, or a port stays in use.

## Starting and stopping

| Symptom | Cause | Fix |
|---|---|---|
| Every command except `--version` and `--help` stops with `APROXY_HOME must be an absolute path…` | `APROXY_HOME` is set to a relative path; aProxy does not resolve it against the working directory | Set `APROXY_HOME` to an absolute path, or unset it to use `~/.aproxy` |
| `Another program is using <addr>. The instance cannot start.` | Another program listens on the port, or an aProxy instance started under a different `APROXY_HOME` (an instance of this home would be reported as already running) | Find the owner (`netstat -ano \| findstr :<port>` on Windows, `ss -ltnp \| grep :<port>` on Linux), then pick another port or ask the user about that program |
| `Cannot bind <addr>: permission denied or the port is reserved. …` | Windows reserves port ranges for Hyper-V/WinNAT; netstat shows no listener | `netsh interface ipv4 show excludedportrange protocol=tcp`, then choose a port outside every range |
| startup.log has `Cannot create control channel <endpoint>: …` and the instance did not start | Another aProxy instance in the same home already uses that port on a different listen address (both can bind TCP, only one can own the control channel), or on Linux/macOS the run directory path is too long for a socket | Give one of the two configs another port; for a long path, use a shorter `APROXY_HOME` |
| `The new instance (pid N) did not become ready in time (process is running)` or a start that gives up after 30 s | The daemon started slowly (antivirus scan on a cold start) or is stuck; an early exit is reported at once instead, with the startup.log excerpt | Read the end of `<home>/logs/startup.log`. If it shows nothing new, run `aproxy status`: the instance may have come up late. A stuck child is not killed by `start`; stop it if it is not serving |
| Start prints `Configuration errors:` followed by lines like `config.toml:3:1: key: message [code]` | The config has an error: TOML syntax, an unknown key, a wrong type or value, a missing key, a conflict or an unsupported shape. A line names settings.json instead when the value came from a global default | Fix each line; config-toml.md, "Checks at start" explains the codes. `aproxy doctor` also checks every config, and `aproxy config show --effective` reports the same diagnostics without starting |
| `listen_addr has no port or the port is not valid` | `listen_addr` without `:port` | Write it as `127.0.0.1:12345` |
| `aProxy is already running on this port:` | That port's instance is running | Nothing to start. To apply config changes, `aproxy restart <port>` |
| `Port <port> is in use by an aProxy instance listening on <addr>. …` | Instances are identified by port | Give one of the two configs another port |
| `Warning: Listening address … is not a loopback address. …` | `listen_addr` is `0.0.0.0`, a LAN address or a hostname; any host that reaches the port can use the upstream, and the configured key if any | Use `127.0.0.1:<port>` unless the user wants LAN access; then only on a trusted network |
| `There are N running instances. Specify a port, alias or all:` | `stop` or `restart` without a target while several instances run | Pick the instance the user means from `aproxy status`. Use `all` only when the user asked for every instance |
| `Pid N received the stop request but has not exited. …` | Still shutting down (open requests get 10 s), or hung | Run `aproxy status` after a few seconds; if it is still listed, `aproxy stop <port> --force`. Prefer that to killing the pid yourself: it verifies the process identity and removes the desired-state record, so the watchdog does not bring the instance back |
| `Pid N did not respond to the stop request (…). To terminate it, run aproxy stop <port> --force.` | The process is alive but its control channel is broken: it hung | `aproxy stop <port> --force` |
| `status` lists `Unresponsive aProxy instances (…): the processes are running but do not answer on the control channel:`, or `stop` says `… is running but does not respond on the control channel. Use --force to terminate it.` | The instance hung: its process is alive but answers neither requests on the control channel nor a graceful stop | `aproxy stop <port> --force` (or `aproxy restart <port> --force` to bring it back). With the watchdog on, it also terminates and respawns a hung instance by itself |
| After the 0.2.0 binary replaced 0.1.x, a port the user's instance used is still busy and `aproxy status` lists nothing on it | A 0.1.x instance still runs there. The current CLI neither lists 0.1.x instances (their records have another name) nor reaches their control channel, so its `stop --force` and `install --force` cannot end them | Stop it with the 0.1.x binary, under the same home, once the user agrees: compatibility/renamed-keys.md, end of "settings.json keys renamed in 0.2.0", has the steps |
| The proxy answers on a port but `aproxy status` does not list it | The instance runs under another `APROXY_HOME`: its registry and control channel belong to that home | Run `aproxy status` (and `stop`, `logs`) with the same `APROXY_HOME` the instance was started with |
| Port still busy after `aproxy stop` | Shutdown not finished yet (up to about 12 s); or the process had been killed outside aproxy and the watchdog respawned it; or another program owns the port | `aproxy status`: an instance listed on that port is running (respawned), so stop it with `aproxy stop <port>`. Otherwise find the owner with netstat or ss |
| `Port N was not restarted: preflight failed. The old instance is still running.` | The edited config is invalid, or its new port is taken | Fix the reason printed below it; the old instance is still serving |
| `Stop was not confirmed on port N. Restart was aborted. …` | The old instance did not exit | `aproxy status`, then `aproxy restart <port> --force` if it is hung |
| `Restart failed on port N. The old instance has stopped and service is interrupted: …` | The new instance failed to come up; the message includes the new startup.log lines. The desired-state record was kept | Fix the cause, then run `aproxy restore` (the watchdog also retries if it is enabled). No `--config` or one-off flags are needed: the record holds the full launch spec |
| `Port N was not restarted: this instance has no launch record. Restart foreground instances in their own terminal. The old instance is still running.` | A `--foreground` instance: it has no desired-state record | Stop it in its terminal and start it in the background |
