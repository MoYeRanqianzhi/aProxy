用户 2026-10-11 定下 0.2.0 的方向：

- **去掉全部兼容，包括 0.1.0 的原地升级兼容**（`src/compat_0_1_0.rs` 的 S1–S5、install 的 relaying 豁免、
  `tests/compat_v0_1_0.rs`、CI 的 upgrade-from-0-1-0 任务）。0.1.0 用户重新安装。
- **前瞻性与稳定性优先**：用户极少，这是去兼容、改契约最好也是最后的廉价时机；0.2.0 之后对外接口要长期稳定。
- **0.1.0 的内容不默认优秀**：此前的模型较弱，留下不少问题；要有自己的判断，允许大规模重构。
- **文本语言**：给用户看的（命令行输出、`--help`、UI）做 i18n，随语言环境切换（en / zh-CN）；给 agent 看的
  或用户看不见的（日志、发给 HTTP 客户端的错误体与流终态事件、IPC 线上文本、信封 error、skill、`--help`
  末尾的 skill 提示行）固定英文。
- **代码注释、CHANGELOG、docs、`.agents` 记录保持中文**，不改。
- **UI 是 Tauri 2，编进 aproxy 本体，默认启用**；用条件编译（cargo feature）另出无 UI 版本。这推翻了
  10-04 审查「独立二进制」的建议。用户已有的两个 skill（tauri-custom-titlebar、tauri-windows-mica）的做法
  要用上；Mica 默认关闭，在 UI 设置里开启，要考虑没有 Mica 的 Windows 11。
- **新增 `aproxy skill` 命令**：只下载 skill 的 `skill install/upgrade`，能直接用命令查看 skill 内容（给
  读不了目录的 agent），不能被借来读别的文件；本地没有 skill 就提示，不把 skill 嵌进二进制；`--help`
  末尾加一行提示 agent 有 skill 可看。细节在计划里。

**Why:** 以上是用户的产品决策，不是推导出来的；理由就是上面每条后半句。

**How to apply:** 0.2.0 期间改任何对外可见的东西（IPC、磁盘布局、config/settings 字段、CLI、HTTP 错误体、
信封）都按「之后冻结」来设计，不再为 0.1.0 留读旧逻辑；新写的字符串先判断给谁看，再决定 i18n 还是固定英文；
UI 相关一律走 `ui` feature，无 UI 版本不能因此多出任何依赖。

**Evidence:** 用户 2026-10-11 原话：「去掉兼容后直接开始发0.2.0，这个版本同时开始加入UI……当前用户极少，
是最佳的去除兼容时机……必须要有前瞻性、稳定性的设计。给用户的需要i18n，给agent的或者不可见的固定英文」；
「1的改版，tauri放在本体中，默认内置，通过条件编译额外编译无UI版本」；「读取两个tauri skill，使用其中
技术。其中mica作为可选，默认不启用，但是可以在ui设置中启用。需考虑win11无mica」。

**Recheck when:** 用户改变以上任一方向；0.2.0 发布后（此条转为历史，永久接口另记）。
