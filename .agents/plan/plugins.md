## 来由

用户 2026-11-23 受桌面扩展设计的启发：给 aproxy 本体也做扩展，不只是 format，而是完全强大的扩展——想要 TUI 可以做
TUI 插件，嫌 Tauri 慢可以换别的界面框架。核心想法是插件直接接 IPC 通讯，并在启动 aproxy 时运行某条命令。随后澄清：
插件不是自己去找实例的第三方客户端，而是在启动时就拿到相关信息；启动方式与 format 类似，但在后台，aproxy 不管它是否
持续运行，因为入口程序本身可能只是拉起插件自己的看门狗或后台服务。

## 用户定下的（2026-11-23）

1. **声明在 config.toml**：不同实例可能需要不同插件，所以跟着实例的配置走。全局的另见第 6 条。
2. **名字叫 plugin**，配置里是 `[[plugin]]`。与桌面窗口的扩展包（`kind: "extension"`、`<home>/desktop/extensions/`）是两种东西。
3. **安全靠启动时检查**：实例启动后一般只在关机时结束，或改了配置后 restart，所以可以在插件运行之前做一次基础扫描；
   用户也可以手动设一个参数，写上跳过检查的插件名。目的是不让未知插件被偷偷装上。
4. **用法接近 format**：不规定位置、语言、写法，完全自由。
5. **插件只管理声明了它的配置**（用户纠正主代理时说明）：有多少个配置注册了这个插件，插件就能使用多少个，不是默认管理
   全部配置。插件作为程序在技术上有全部权限，但规范是：没有安装这个插件的配置，插件不应该去管理，否则违背用户的意愿。
   主代理先前说「界面类插件管的是整个 home、所以倾向声明在 settings.json」，是理解错了。
6. **settings.json 可以声明全局插件**（用户补充）：相当于默认值，等效于每个 aproxy 配置里都写了一行这个插件。

## 设计草稿（主代理的建议，用户尚未逐条确认）

**全局插件（落实第 6 条）。** 不能放在 settings.json 的 `defaults` 下：`defaults` 是整键替换，配置里没写这个键才用默认值，
配置一写自己的 `[[plugin]]` 就把默认的整个取代了，与「每个配置都多一行」不同。所以单列一个键（名字实现时定），语义是追加：
每个实例实际的插件 = 全局插件 + 本配置的插件，交接也按这个顺序（第 13 条：后面的覆盖前面的）。由此：全局插件的管理范围是全部配置，包括以后新建的；启动时检查同样适用；
状态里的 `plugins[]` 注明每个插件来自 settings.json 还是配置。settings.json 也对不认识的键报错，写了这个键之后换回不认识它的
旧版本，所有命令都会因 settings.json 出错而停下（强制安装不读配置与 settings，不受影响）；给作者与用户的文档写明最低版本。
还要定两件事：配置里有同名插件时，以配置的为准（可以按实例改参数）还是报错（按「启动交接」的原则 5 建议先报错：两份同名插件
会用同一个 format 前缀、同一个数据目录，以后要放宽也不破坏谁）；某个配置不想要某个全局插件时怎么排除。

**管理范围（落实第 5 条）。** 插件的范围是声明了它的那些配置，以及从这些配置启动的实例：
- 每次拉起都带着触发它的那个实例与配置（见「启动交接」的请求，含 `instance.config_path` 与 `plugin.name`）。入口幂等时的常见做法是：
  服务已在跑，就把这一次的实例信息交给服务再退出，服务由此知道自己被哪些配置注册。这是给作者的文档里要写的模式。
- 服务自己重启后要能重新得出范围：`aproxy status --json` 与状态快照里每个实例带上它的配置声明的插件（下面的 `plugins[]`），
  插件从中找出声明了自己的那些。按什么认出自己（条目名、解析后的命令路径）实现时定。
- 范围内的事：这些配置的实例的状态、停止、重启、请求历史、日志，以及改这些配置文件。范围外的事：别的配置与它们的实例，
  以及影响整个 home 的操作（安装与升级会滚动重启全部实例、`stop all`、settings.json 的全局默认）。
- 规范管不住程序本身的权限，所以这一条靠文档讲清楚、审查来查：插件去管没有声明它的配置，审查 skill 按不合规的危险信号处理，
  与扩展把数据写到自己的存储之外同等对待。

**配置条目。** `name`（必填，规则见「启动交接」的「插件名与数据目录」；在本配置内唯一；跳过检查、数据目录、format 前缀、
日志都按它认）、`command`、`args`、`env`、`timeout_secs`（交接期限，默认 10），解析规则与 `[[format]]` 相同：裸名先找 `<home>/bin/` 再找 PATH，相对路径相对 home。config.toml 对不认识的键一律报错、实例不启动
（有意如此，见 aproxy-cli skill 的 config-toml.md），所以写了 `[[plugin]]` 的配置在旧版本上起不来；给作者的文档写明最低版本。

**什么时候拉起、交给它什么、怎么拉起。** 都在下面「启动交接：插件协议 1」一节。原先这里的三段（控制端点应答之后拉起、
拉起即走、用一组 `APROXY_*` 环境变量交信息、标准流接空）已被那一节取代：第 1 种写法要在启动时交回配置覆盖（第 8 条），
第 12 条又要求插件必须应答。不变的是：实例每次启动都拉起一次；不登记台账（C3 只管 aproxy 自己的进程）；看门狗不守护插件（第 10 条）。

**IPC 的兼容性够不够。** 机制够用：`v` 只在语义不兼容时递增，加 op、参数、字段、错误码、状态值都不递增，读者忽略不认识的
（`aproxy-ipc/src/wire.rs:200`）；快照里的 `ops` 与 `features` 供双方协商；`tests/contract_v0_2.rs`（控制协议与盘上记录）
和 `tests/json_docs.rs`（各命令的 `--json`）守着只增不改。要补的：
- 写明出了 v2 之后 v1 至少再支持多久。现在只规定了何时递增，没规定旧版本留多久；插件交接时从 `ipc.protocols` 知道实例会说哪些版本，能自己降级，
  所以不必承诺永久。
- 插件协议 1（交接的时机、请求与回复、`[[plugin]]` 的字段）是新的公开接口，同样只增不改，进契约测试。
- IPC 只管单个实例：状态、停止、请求历史、订阅（t10c 再加 format 重启与 control）。启动与重启实例、改配置、看日志在命令行
  一侧，插件用 `aproxy … --json`，两套都算公开接口。插件只对自己范围内的配置与实例用它们（见「管理范围」）。
- 每个实例至多 8 条订阅连接（`src/history.rs` 的 `MAX_SUBSCRIBERS`），插件多了要放宽。

## 启动时检查（方向已定，细节待定）

实例拉起插件之前先检查。被拦下的插件不运行，也就没有应答，按第 12 条实例启动失败（原先写的「检查不阻塞实例启动」已作废）；原因进实例日志、状态快照（新增可缺省的
`plugins[]`：本配置声明的每个插件，以及它已拉起、被拦及原因、拉起失败或跳过了检查）、`aproxy start` 的输出、
`aproxy doctor` 与桌面界面的实例页——开机恢复这类无人值守的启动里被拦，用户要能看到为什么插件没跑。按程序文件的指纹
缓存结果，没变的不重扫。

扫描的信号与 TODO 里「安全加固：安装时自动识别典型危险信号」共用一份，从三个审查 skill 的 `references/signals.md` 起步，
例如：命令行里的下载即执行与编码命令（`curl … | sh`、`powershell -enc`、`mshta`）、程序放在临时目录或下载目录、Windows 的
网络来源标记（Zone.Identifier）与 macOS 的隔离属性、参数里的脚本文件含混淆或 webhook 与隧道地址、读 config.toml 与
settings.json 里的 key、写开机自启。

检查的边界：home 里的任何记录，同一用户的程序都改得了，所以挡不住已经以用户身份运行的恶意程序。它挡的是替用户改配置的
agent 与脚本（包括被提示注入的 agent）和误操作，并让「跳过检查」成为显眼、可审查的一步。这与桌面扩展「防御只在安装前有效」
的思路一致（记忆 desktop-extension-trust）。

**待用户定的三个问题（主代理 2026-11-23 提出）：**
1. **跳过绑定什么。** 只认名字的话，换掉同名插件背后的程序就绕过了扫描。建议跳过记录同时绑定命令行与程序文件的哈希，变了
   就重新扫；跳过名单也不放在 config.toml，否则「加插件」和「加跳过」是同一次编辑。
2. **未知但看起来干净的插件。** 内容扫描认不出它。若要挡住一切未经用户同意加进来的插件，需要「首次出现确认一次」：新加的或
   变了的插件，用户确认一次之后才运行，确认时给出扫描结果。代价是每加一个插件多一步。
3. **format 有同样的口子。** format 程序同样在实例启动时由 aproxy 拉起，还看得到全部请求与密钥；只查插件，偷偷加一个
   `[[format]]` 就绕过去了。若把 format 也纳入检查，升级时已有的条目要自动视为已确认，否则升级后 required 的 format 被拦，
   请求全部失败（`format_unavailable`）。

**IPC + format 的自由度分析（主代理 2026-11-26，用户未逐条确认）。** 结论是够用：
- 数据路径靠 format：改请求、选上游与轮换 key、按请求覆盖重试与超时（`overrides`）、拒绝（`fail`）、决定重试与等多久
  （`decide`）、改响应与流、生成心跳、`notify` 收每个请求的结局、`report` 显示在日志与界面。format 还能把 `url` 改到插件自己起的
  本地 http 服务上，插件就能自己回答请求（缓存、模拟、本地模型），所以不需要在实例的端口上开放注册路由。
- 观察与控制靠 IPC 与 `--json`：状态快照、请求历史与体、实时订阅；停止与重启实例、重启 format；`format_control` 让插件与它预设的
  format 对话（每次 5 秒、同时一个、参数 64 KiB，大量通讯应由插件与 format 自己开通道，文档写明即可）。改配置走 `aproxy config`。
- 实例级设置（端口等）只能改配置再重启；热改的需求大多由按请求的 `overrides` 与 format 自己重读文件满足。
- 插件本身的部分（启动时的交接、只在找不到内置命令时才查的命令登记、启动时合并预设）都不在请求路径上。请求路径上的代价
  只有预设带来的 format：链上每多一个 format、每多一个阶段，每个请求就多一次进程间往返，给预设插件作者的文档要写明。

找到的缺口：
- **用户在终端里运行的插件命令（如 TUI）怎么找到实例的控制端点。** `aproxy status --json` 不含端点名（2026-11-26 核对
  `aproxy-ipc/src/wire.rs:12` 的 `InstanceRecord`，没有这个字段）。主代理先提议给 status 加字段；用户给出了不需要新入口的做法
  （下面「插件的标准写法」），由插件在被拉起时自己记下实例信息，所以不加。
- **订阅上限每实例 8 条**（`src/history.rs:47` 的 `MAX_SUBSCRIBERS`），桌面窗口、`aproxy logs` 与几个插件一起就可能用完。补法：放宽，
  或者用完时让应答说清是满了。

有意不给的（会影响性能、体积或稳定性）：进程内插件（动态库或 WASM 运行时，体积以 MB 计，崩溃会带走实例）、在实例端口上注册
HTTP 路由（用改 `url` 到插件自己的服务代替）、命令行的前后钩子、看门狗守护（第 10 条）。

**插件怎么写（用户 2026-11-26）。** aproxy 只在启动时按标准格式把信息交给插件，插件怎么用是插件自己的事：不强制存文件，也不强制
有守护进程。用户随后澄清（原话）：「实际上不强制储存文件，只是传递给插件，插件怎么用是插件的事情，我这里提到储存文件是因为当前
aproxy会在/run下面储存pid等信息。另外没有强制要求存在守护进程，最简单的插件可以只在传递了配置覆盖信息后就退出。另外一种简单的插件
则是启动后一种运行，而不是单独启动另外的守护进程」（「一种运行」按上下文理解为「一直运行」）。三种写法都合规，作者文档拿它们当范例：
1. **只给配置覆盖就退出**：例如多 format 预设插件，被拉起后交出配置覆盖（预设的 format 等），然后退出。
2. **自己一直运行**：被拉起后就一直跑，不另起守护。每个声明它的实例启动时各拉起一份。
3. **入口加共享守护**（用户以 TUI 为例）：`[[plugin]]` 的命令是 `aproxy-tui start`；入口收到本实例的信息后，看自己的后台守护是否活着，
   没活着就在同时启动的几个入口之间选出唯一一个去拉起它（选举由插件自己做，例如独占锁或绑定一个固定的本地 socket）。守护定期检查
   注册了这个插件的实例，记下或去掉它们（可以像 aproxy 在 `run/` 下记 pid 那样存文件，也可以不存）。用户运行插件注册的全局命令
   `aproxy tui`，TUI 经 IPC 实时取这些实例的信息。只取注册了插件的实例，是第 5 条的要求：技术上全都拿得到，但用户只让这些配置用它。
aproxy 要提供的只有启动时的交接，其余全由插件自己做，符合第 11 条。原先草稿里「入口必须幂等」只适用于第 3 种，不是对所有插件的要求。

第 3 种写法的几处细节，写进作者文档（建议，用户未确认）：
- **认准实例**：同一端口上新起的实例端点名相同，检查时要比对 IPC 快照里的 `instance_id`，不能只看端点能不能连上。
- **守护停了没人拉**：看门狗不守护插件（第 10 条），实例不重启就不会再拉起入口，所以 `aproxy tui` 启动时也要检查守护、按同样的选举
  拉起它。
- **加插件之前已在运行的实例**：下次启动（restart）才会交接；改配置本来就要 restart，可以接受。
- **要不要显示已停的实例**（以便在 TUI 里启动它）：若要，按配置（`instance.config_path`）而不是按实例记，实例关了标为停止而不是去掉。

**还要定的细节（主代理的建议，用户未确认）：**
- **命令怎么注册。** 插件调用一条 aproxy 命令登记（例如在它第一次运行时），还是往 home 里一个约定的位置写文件；登记了什么
  （命令名、要运行的程序与参数）、怎么注销、插件删掉后留下的登记怎么发现（`aproxy doctor` 报出指向不存在程序的命令）。
- **命令的约束。** 内置命令永远优先，任何插件都不能遮蔽；`install --force` 属于冻结契约 C1–C8，尤其不能被遮蔽。以后新增的内置命令
  会让同名插件命令失效，注册时与 `aproxy doctor` 都要报出冲突，给作者的文档写命名建议。`--help` 把插件命令单列并标明第三方，
  因为 skill 教 agent 放心运行 `aproxy` 开头的命令，伪装成官方命令的插件命令更容易骗过 agent。注册命令本身也要受检查（插件命令
  是用户在终端里运行的，不经过实例启动时的检查，检查放在注册时或运行时，待定）。打错命令时的提示要同时说明没有这个插件命令。
  插件命令的 `--json` 与退出码不受我们约束，skill 要告诉 agent。
- **预设怎么交、怎么合并。** 已定（第 13、17 条），细节见「启动交接：插件协议 1」的「顺序与合并」。
- **检查。** 预设带进来的 format 程序看得到全部请求与密钥，必须与插件一起受启动时检查（与「启动时检查」第 3 个问题相连）。

## 启动交接：插件协议 1

**状态**：要点由用户 2026-11-26 定下（第 12 到 18 条）；下面的细节是主代理按这些要点写的设计稿，等用户过目。

用户的要求（2026-11-26 原话）：「思考一下这传递内容的标准格式，要稳定好用，避免后续容易改动，现在就要想好一个稳定设计」。

**设计原则**
1. **回复不可省略**（第 16 条）：固定的行数、每行固定的键、全部必填；没有内容的行写 `{}`；最后一行明确写成功或失败。aproxy
   对回复从严：少一行、多一个键、缺一个键、出现 null、出现不认识的值，都算无效回复，实例启动失败。拼错的键不会被悄悄忽略。
2. **回复的形状按协议版本冻结**：协议 1 的四行永远是这四行，每行的键永远是这些。要让插件多交东西，就出协议 2，或定义一个
   feature，由插件在第 1 行里明确选用；aproxy 读完第 1 行就知道后面还有几行、每行是什么。aproxy 永远接受协议 1。
3. **请求只加字段，这是唯一一处容忍**：请求写在协商版本之前，所以插件要忽略请求里不认识的字段，否则 aproxy 加任何信息都会
   弄坏所有已有插件。往请求里加的只能是插件不理会也不出错的信息；凡是要插件改变回复的变化，一律走新协议版本或插件选用的 feature，
   aproxy 不会悄悄改变对旧插件的要求。请求里每个键都一定出现，没有「缺了就表示默认」的键。
4. **复用已冻结的形状，不另造词汇**：`instance` 就是实例记录 `InstanceRecord`（`aproxy-ipc/src/wire.rs:12`，即
   `run/<端口>.instance.json` 与 IPC 快照里的 `instance`）；配置用 config.toml 的键名与层级写成 JSON（与 settings.json 的
   `defaults` 同一种写法），密钥用 `aproxy config show --json` 的占位 `{"secret":true}`，来源沿用 `config show --effective` 的
   `sources` 词表（`src/config/resolve.rs:48`：`override`、`toml`、`settings`、`env`、`default`），只多 `unset` 与 `plugin:<名字>`。
5. **拿不准的先定成报错**：报错以后可以放宽成某种行为，不会让任何现有的插件或配置坏掉；定成某种行为就再也改不回来。
6. **一次交接就是一次真正的启动**：实例每次启动（start、restart、restore、看门狗重拉、升级时的滚动重启）对每个插件各交接一次，
   别的时候不交接，也没有「试运行」。插件可以放心在交接时做有副作用的事（拉起守护等）。

**顺序与合并（第 13、17 条）**
- **逐个交接**：先 settings.json 的全局插件，再本配置的 `[[plugin]]`，各按书写顺序，一个回复完才拉起下一个。第 i 个插件拿到的是
  它下面所有层合成后的完整配置，它的回复叠在最上面，结果再交给第 i+1 个。
- **层次**（低到高）：内置默认 < settings.json 的 `defaults` < config.toml < `start` 的覆盖参数 < 各插件（按交接顺序，后面的高）。
  即插件压过用户写的一切，包括 `start` 的覆盖参数（第 13 条：「插件压过用户设置的」）；后面的插件覆盖前面的。插件不能设的键
  （见下）不受影响，所以 `--listen-addr` 与 `--log-file` 照常生效。
- **叠一层的规则**与现有各层相同：标量按叶子覆盖；数组整个替换；两张请求头表按头名合并、同名以上层为准。`api_key`、`proxy`、
  `proxy_username`、`proxy_password` 按现有规则写空串就是「未设置」，插件用它清掉下层的值。回复里不能有 null（TOML 没有 null）。
- **format 列表**：插件的配置行里给了 `format`，就是给出完整的新列表，替换下层的；没给就原样保留。每一项要么是
  `{"keep":"<名字>"}`，原样保留视图里的这一项（连同插件看不到的密钥，插件不必也不能重写它）；要么是这个插件的新条目，名字必须写成
  `<插件名>/<名字>`。视图里没有被 keep 的条目就被去掉，顺序就是插件给的顺序，所以插件能把自己的条目放在链上合适的位置
  （例如换 key 的程序必须在链尾）。keep 一个不存在的名字、同一个名字 keep 两次、新条目不带自己的前缀、结果里有重名，都是错误。
- **每一步都校验**：每个插件回复之后，立刻按 config.toml 的规则完整校验一次合并结果（「必填」这类检查除外，例如 `base_url`，
  留到最后一个插件之后再查），不通过就算这个插件的错，实例启动失败。所以每个插件拿到的都是一份合法的配置。
- **不能设的键**：`listen_addr`、`log_file`、`plugin`。前两个在交接之前就已用掉（端口决定实例的身份与控制端点，日志在读配置时
  就已打开），插件也不能再声明插件。以后新增的配置键，在它出现的那个版本里就定下插件能不能设。
- **只对这一次启动有效**：要换一套覆盖，就重启实例、重新交接。`aproxy restart --format` 只重启 format，用的仍是这次启动合成的配置。
  插件被删，下次启动它的覆盖与它的 format 就都没了。

**进程与传输**
- **拉起**：`[[plugin]]` 的 `command` 与 `args`，不经过 shell，解析规则与 `[[format]]` 的 `command` 相同（裸名先找 `<home>/bin/`
  再找 PATH；相对路径相对 home；Windows 拒绝 `.cmd` 与 `.bat`）。工作目录是 home。环境继承实例（其中已有 `APROXY_HOME`，见
  `src/main.rs:98`），再加上条目的 `env`；不另设 `APROXY_*` 变量，信息都在请求里。与实例分离：Windows 上不建控制台窗口、不在
  实例的作业对象里，unix 上自成会话（前台实例被 Ctrl-C 时插件不跟着收到信号）；不登记台账，实例退出时也不结束它。
- **时机**：实例占住端口与控制端点、写下实例记录之后（此时 IPC 已能应答，状态是 `starting`），format 握手与开始服务之前。
- **stdin**：aproxy 写入一行请求（一个 JSON 对象加 `\n`），之后在协议 1 里不再写任何东西，但管道一直开着，直到实例进程退出。
  **stdin 读到 EOF，就表示拉起你的那个实例已经不在了**：与实例同生共死的插件（第 2 种写法）靠它就知道何时退出，不必轮询 IPC，
  也不会在实例反复重启后留下一堆旧副本。所以插件要读一行就处理，不能读到 EOF 才处理（那要等到实例退出，交接早已超时）。
- **stdout**：插件按顺序写四行回复（见下），每行写完 flush。第 1 行之前不能往 stdout 写别的（库打印的横幅也会让回复无效）；
  第 4 行之后也不要再写，协议 1 在那里没有定义任何东西，多出来的行作为协议违规记进实例日志（不改变交接的结果）。
- **stderr**：从拉起到实例退出，逐行进实例日志，前缀 `plugin[<名字>]`，已知的密钥先替换掉；每行截到 8 KiB，每个插件每秒至多
  50 行（与 format 相同）。交接失败时，错误里带上 stderr 的最后几行。
- **三根管道在实例退出时都会断**：插件另起的守护进程不要继承它们（给守护自己的标准流，例如接空设备或写自己的日志），否则实例
  一退出，守护写 stdout 或 stderr 就会出错，unix 上还可能被 SIGPIPE 结束；守护也不该把继承来的 stdin 的 EOF 当成退出信号，那只说明
  最初拉起它的那个实例退出了。
- **期限**：拉起之后 `timeout_secs` 秒内（条目里设，默认 10，不能为 0）要收到完整的四行。超时、第 4 行之前退出、回复无效，aproxy
  结束这个插件进程（只结束它本身），后面的插件不再拉起，实例启动失败（第 12 条）；前面已经回复的插件不动，它们会收到 stdin 的 EOF。
  第 4 行之后，插件退出与否、退出码是多少，aproxy 都不管。实例的启动时间是各插件交接时间之和。
- **格式**：线上只有 JSON（第 18 条）：请求是一个 JSON 对象，回复的前三行各是一个 JSON 对象，第 4 行是一个英文词；从不传 TOML
  文本，配置只是沿用 config.toml 的键名与层级。
- **编码**：每一行都是 UTF-8；第 1 行开头的 BOM 与每行 `\n` 前的 `\r` 忽略；每行连同换行至多 1 MiB，超过的不读完就算无效。

**请求（aproxy 写给插件的一行）**

示例（Windows，实际是一行，这里折开只为阅读；`config.values` 与 `config.sources` 只列了几项，实际列出全部的键）：

```json
{"v":1,"protocols":[1],"features":[],
 "home":"C:\\Users\\me\\.aproxy","aproxy_exe":"C:\\Users\\me\\.aproxy\\bin\\aproxy.exe",
 "plugin":{"name":"tui","source":"config","data_dir":"C:\\Users\\me\\.aproxy\\data\\plugins\\tui"},
 "instance":{"pid":4242,"start":"…","instance_id":"19ac3f2e8b5d1a2b","version":"0.3.0","listen_addr":"127.0.0.1:12345",
   "config_path":"C:\\Users\\me\\.aproxy\\configs\\work.toml","base_url":"https://api.example.com",
   "started_at":1764000000000,"log_path":"C:\\Users\\me\\.aproxy\\logs\\aproxy-12345.log","foreground":false},
 "ipc":{"endpoint":"\\\\.\\pipe\\aproxy-0123456789abcdef-12345","protocols":[1]},
 "config":{"values":{"base_url":"https://api.example.com","api_key":{"secret":true},"proxy":null,"delivery":"retry",
     "timeouts":{"connect_secs":30,"first_byte_secs":300,"read_idle_secs":300},"extra_headers":{},
     "format":[{"name":"convert","command":"aproxy-format","args":["convert"],"env":{},"process":"persistent","stages":["request","stream"],"…":"…"}]},
   "sources":{"base_url":"toml","api_key":"settings","proxy":"unset","delivery":"default","timeouts.connect_secs":"default","format":"toml"},
   "withheld":[]}}
```

| 字段 | 含义 |
|---|---|
| `v` | 永远是 1：这一行的形状只加不改。 |
| `protocols` | 实例会说的插件协议版本；插件从中选一个，写进回复第 1 行的 `protocol`。 |
| `features` | 实例支持的可选行为。协议 1 没有定义任何一个，所以是 `[]`。 |
| `home` | home 的绝对路径（与环境里的 `APROXY_HOME` 相同）。 |
| `aproxy_exe` | 正在运行的 aproxy 可执行文件的绝对路径。插件调命令行用它，不会调到 PATH 里的另一个版本；原地升级后同一路径就是新版本。 |
| `plugin.name` | 这个插件的条目名。 |
| `plugin.source` | `"settings"`（settings.json 的全局插件）或 `"config"`（本配置的 `[[plugin]]`）。 |
| `plugin.data_dir` | 这个插件的数据目录，aproxy 已经建好（见「插件名与数据目录」）。 |
| `instance` | 实例记录，与 `run/<端口>.instance.json`、IPC 快照的 `instance` 是同一个对象，规则相同（只加字段）。`config_path`（没有配置文件时）与 `log_path`（前台实例）可以是 null。`base_url` 是交接开始前的值（已脱敏，只供展示；没设时为空串），实例开始服务之前会按合成结果重写记录。认实例用 `instance_id`（每次运行都不同）：同一端口上新起的实例，端点名与旧的相同。 |
| `ipc.endpoint` | 控制端点：Windows 是命名管道名，unix 是 socket 路径。插件不必照着 `aproxy-ipc/src/endpoint.rs` 自己算（规范化路径再哈希，别的语言照抄容易在 subst 盘符与目录联接上算错）。 |
| `ipc.protocols` | 实例会说的控制协议版本，现在是 `[1]`。 |
| `config.values` | 到这个插件为止合成的完整配置（第 17 条）。**这个版本认得的每个键都出现**：没设的是 null，表、数组为空时是 `{}`、`[]`；format 的每一项都填齐全部字段（含默认值）并用最终的名字。密钥（`api_key`、`proxy_password`、密钥类请求头的值、format 的 `env` 的值，以及 `config show` 会打码的参数）一律是 `{"secret":true}`。插件据键是否出现，就知道这个版本认不认得某个键，不必比较版本号。 |
| `config.sources` | 每个键的值来自哪一层，键与 `values` 一一对应：叶子用点分路径（`timeouts.connect_secs`），请求头按头名（`extra_headers.x-foo`），数组与 format 列表按整个键（`format`）。取值：`default`、`settings`、`toml`、`override`（`start` 的覆盖参数）、`env`（只有 `proxy`）、`unset`、`plugin:<名字>`。读者把不认识的取值当作「另一层」。 |
| `config.withheld` | settings.json 全局默认里因目标不同而没有继承的凭据，形状与 `config show --effective --json` 的 `withheld` 相同；没有时是 `[]`。 |

请求里没有密钥的明文。插件确实要用 key 的（例如生成换 key 的配置），只能自己去读配置文件；这样做在审查时看得见，审查 skill 会要求
它讲清理由。

**回复（插件写给 aproxy 的四行，第 16 条）**

成功时：

```
{"v":1,"protocol":1,"name":"aproxy-tui","version":"1.2.0","features":[]}
{}
{}
success
```

拒绝启动时：

```
{"v":1,"protocol":1,"name":"aproxy-tui","version":"1.2.0","features":[]}
{}
{"code":"missing-dependency","reason":"The terminal UI needs aproxy 0.3.0 or later."}
failure
```

| 行 | 内容 | 规则 |
|---|---|---|
| 1 身份 | `{"v","protocol","name","version","features"}` | 五个键都必须有，不能有别的键。`v` 是 1；`protocol` 从请求的 `protocols` 里选，现在是 1；`name`、`version` 是插件程序自己的名字与版本（各 1 到 64 字节，不含控制字符），显示在 status、doctor 与日志里，审查时据此认出实际跑的是什么；`features` 是插件选用的可选行为，协议 1 里只能是 `[]`。 |
| 2 配置 | 叠在当前配置上的一层，不覆盖任何东西就写 `{}` | 写法见「顺序与合并」。失败时必须是 `{}`。 |
| 3 失败说明 | 成功时 `{}`；失败时 `{"code","reason"}` | `code` 是插件自定的短词（1 到 64 字节，字母、数字、`-`、`_`、`.`），`reason` 是给人看的一句英文（1 到 1024 字节）。 |
| 4 结果 | `success` 或 `failure` | 小写 ASCII，整行就是这个词。 |

`success` 而第 3 行不是 `{}`、`failure` 而第 2 行不是 `{}` 或第 3 行不完整，都是无效回复。第 4 行用英文词而不用「成功」「失败」：
Windows 上的 Python 与 PowerShell 5.1 默认按系统代码页（中文系统是 GBK）往管道写，非 ASCII 的字会变成别的字节，插件明明成功了
也会被判成无效回复；JSON 里的非 ASCII 可以写成 `\u` 转义，所以前三行不受影响。

Python 写法示例（给作者文档用）：

```python
import json, sys
req = json.loads(sys.stdin.readline())          # 读一行，不要读到 EOF
cfg = {}                                         # 要覆盖的配置，看 req["config"] 决定
for line in ({"v": 1, "protocol": 1, "name": "my-plugin", "version": "1.0.0", "features": []}, cfg, {}):
    print(json.dumps(line), flush=True)          # json.dumps 默认把非 ASCII 转义
print("success", flush=True)
```

**插件名、format 名与数据目录**
- `[[plugin]]` 的 `name` 必填，规则 `[a-z0-9][a-z0-9_-]{0,31}`，不能是 Windows 的设备名（`con`、`prn`、`aux`、`nul`、`com1`–`com9`、
  `lpt1`–`lpt9`），在一份配置里唯一。只用小写，免得在不分大小写的文件系统上撞名。这个名字同时是 format 的前缀、数据目录名与日志前缀。
- **format 名字里的 `/` 留给插件**（第 14 条）：用户在 config.toml 里写的名字不能含 `/`，从 0.2.0 起就这样校验（任务 t18）；插件的
  新条目叫 `<插件名>/<名字>`，后半段照常规则且不含 `/`。名字出现在 status、日志、`aproxy restart --format tui/keys` 与
  `format_control` 里，插件调自己 format 的 control 就用这个全名。
- **数据目录** `<home>/data/plugins/<name>/`（第 15 条）：aproxy 在拉起前建好，从不自动删除；所有配置里同名的条目共用，第 3 种写法
  的守护可以把共享状态放在这里。新增目录要对照 C1–C8 冻结的 home 布局，确认只是新增（2026-11-26 查过，home 下现在没有 `data`）。
  format 的数据目录还待用户确认（[w5e-extensions](w5e-extensions.md)），若采用就放 `<home>/data/formats/…`。

**失败与错误码**
- 交接本身的失败用一个码 `plugin_failed`，`details` 里有 `plugin`（条目名）与 `kind`：`spawn`（起不来）、`timeout`、`exited`
  （第 4 行之前退出，带已收到几行与退出码）、`invalid_reply`（带第几行、哪条规则不符，不带内容，因为回复里可能有密钥）、`failure`
  （插件第 4 行写了 failure，带它的 `code` 与 `reason`）、`blocked`（被启动时检查拦下，带原因）。`kind` 是开放词表，读者把不认识的
  当一般失败。
- 插件的配置行没通过校验，用与 config.toml 相同的配置错误码（如 `config_conflict`），位置前面加上 `plugin.<名字>.`。
- 退出码照 format 握手的分法：要改插件、改配置或要用户处理的为 3（`invalid_reply`、`blocked`、配置错误），可能一时的为 1（`spawn`、
  `timeout`、`exited`、`failure`）。看门狗与 restore 遇到这类失败怎么退避，见第 12 条下的待办。

**给作者文档的提醒**
- 交接期间不要对本实例做启停（`aproxy start/restart/stop` 指向它会等它就绪，而它在等你的回复）；要连 IPC 可以连，看到的是 `starting`。
- 只想拉起守护的入口，先把守护放到后台再回复，别让慢的初始化吃掉期限。
- 不覆盖任何东西的插件也必须写满四行。

**以后可以加、都要插件选用的**：拉起原因（普通启动、restore、看门狗、restart、升级）、界面语言、插件的 `report`、经 stdin 推给插件
的后续事件、只检查不启动的试运行、删除下层的键。加法都是新协议版本或新 feature，由插件在第 1 行选用。插件命令的注册（第 7 条）
另行设计，不放进交接：交接是每个实例、每次启动一次，命令是全局的。

**实现时要调整的（不影响协议）**
- **启动顺序**：现在 `serve_forever`（`src/server.rs:53`）先按配置建出代理状态，再占端口与控制端点、写实例记录、握手 format。改成：
  宽松读配置（定日志位置）→ 占端口与控制端点、写记录 → 逐个交接插件，每步合并并校验 → 查必填项 → 建代理状态 → format 握手 →
  重写实例记录 → 开始服务。交接期间 IPC 报 `starting`，请求历史为空。
- **视图**：复用 `config show --effective` 的合成、打码与来源（`src/commands/config.rs` 的 `view::effective_value`、`view::redacted`），
  补上「每个键都出现」与插件层的来源。
- **拉起**：`spawn_detached_with`（`src/daemon.rs:613`）不接管道，要一个接上三根管道、其余照旧分离的变体；unix 上要回收很快就退出
  的插件进程，不留僵尸。
- **状态**：快照与 `status --json` 加 `plugins[]`（条目名、来源、程序回报的名字与版本、结果）；`formats[]` 的每一项加 `plugin`，
  标出它来自哪个插件。`aproxy config show --effective` 不运行插件，看不到插件给的值，要说明这一点并指向 status。
